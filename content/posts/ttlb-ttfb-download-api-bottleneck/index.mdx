TTLB와 TTFB는 백엔드 면접에도 자주 나오는 개념입니다. 책에서 본 대략적인 내용은 알지만, 실무에서 어떻게 쓰이는지 손에 잡히게 본 적은 없었습니다. 이번에 이 개념을 활용할 이슈를 담당하게 되었습니다.

이번 글은 사내에서 발생한 다운로드 API 장애를 추적하면서, 그 과정에서 쓴 두 가지 측정 도구를 정리합니다.

- TTLB/TTFB — 응답이 느릴 때 네트워크와 서버 중 어디가 원인인지 파악하기 위해 측정
- 구간 로깅 — 서버 내부에서 어느 단계가 시간·메모리를 잡아먹는지 파악하기 위해 측정

<strong>이 글에서 다루는 것</strong>

- TTLB/TTFB로 응답 시간을 분해하는 방법과 X-Envoy-Upstream-Service-Time활용
- prefix + elapsed + heap memory를 함께 찍는 구간 로깅 패턴
- 측정값을 컨테이너 한도와 결합해 운영 영향을 역산하는 법

사건의 시작은 단순합니다. 채팅 로그 데이터를 CSV로 변환해 ZIP으로 다운로드 받는 API에서, 고객사가 3개월치를 호출했을 때 서버가 다운되는 장애 이슈가 들어왔습니다. 데이터 규모가 변수일 것이라는 직감이 들었고, 추측을 가설을 증명하기 위해 측정을 진행해 보았습니다.

## 1. TTLB/TTFB — 네트워크와 서버 중 어디가 병목인가?

### 1.1 개념

먼저 API 호출이 일어날 때 시간이 어디서 흐르는지 짚어봅시다. 클라이언트가 요청을 보내면 서버에 도착하고, 서버가 처리한 결과가 다시 클라이언트로 돌아옵니다. 이 흐름의 어느 지점부터 어느 지점까지를 재느냐에 따라 지표 이름이 달라집니다.

<Figure src="/posts/ttlb-ttfb-download-api-bottleneck/02.png" alt="[그림] 요청~응답 과정 모식도" width={1264} height={512}>
  [그림] 요청~응답 과정 모식도
</Figure>

| 지표 | 정의 | 무엇을 알 수 있나 |
| --- | --- | --- |
| TTLB (Time To Last Byte) | 요청부터 마지막 바이트까지 | 전체 응답 시간 |
| TTFB (Time To First Byte) | 요청부터 첫 바이트까지 | 서버가 응답을 시작하기까지 — 단, 네트워크 RTT와 서버 처리가 섞여 있음 |

<p className="table-caption">[표] TTLB와 TTFB의 개념</p>

주의할 점이 있습니다. TTFB가 크다고 곧바로 “서버가 느리다"고 결론 내릴 수 없습니다. TTFB는 ‘<strong>클라이언트 → 서버 RTT + 서버 처리 시간 + 첫 바이트가 돌아오는 RTT’</strong>가 모두 합쳐진 값이기 때문입니다. 네트워크가 느린 환경에서 서버가 멀쩡해도 TTFB가 클 수 있죠.

따라서 <strong>서버 사이드 처리시간을 별도로 알 수 있는 지표</strong>가 함께 필요합니다. 사내 환경은 envoy 사이드카가 응답에 X-Envoy-Upstream-Service-Time 헤더를 적어주고 있어서, 이 값을 TTFB에서 빼면 네트워크와 envoy오버헤드만 분리됩니다.

### 1.2 실제 측정 — Chrome DevTools + envoy 헤더

API를 호출하고 Chrome Dev Tools의 Network 패널로 Timing을 분해했습니다.

<Figure src="/posts/ttlb-ttfb-download-api-bottleneck/04.png" alt="[그림] Chrome Dev Tools로 측정한 Netowrk의 Timing" width={1112} height={892}>
  [그림] Chrome Dev Tools로 측정한 Netowrk의 Timing
</Figure>

```http
Accept-Ranges: bytes
Content-Disposition: attachment; filename=ChatLogs.zip
Content-Length: 3707214
Content-Type: application/octet-stream
Date: Mon, 11 May 2026 01:55:39 GMT
Server: istio-envoy
Vary: Origin,Access-Control-Request-Method,Access-Control-Request-Headers,Origin,Access-Control-Request-Method,Access-Control-Request-Headers
X-Envoy-Upstream-Service-Time: 5664
```

```text
전체 5.91s (= TTLB)
├─ Queueing + Stalled + Request sent ≈ 2.4ms
├─ Waiting for server response = 5.70s (TTFB)
│   ├─ 네트워크 RTT + envoy 오버헤드 ≈ 36ms
│   └─ 실제 서버 처리 ≈ 5,664ms   ← X-Envoy-Upstream-Service-Time
└─ Content Download ≈ 208.8ms (3.7MB / 17.7 MB/s)
```

여기서 envoy 사이드카가 응답에 적어주는 `X-Envoy-Upstream-Service-Time: 5664` 헤더가 결정적이었습니다. 이 헤더는 envoy가 upstream(실제 application)으로 요청을 보낸 시점부터 응답을 받은 시점까지의 시간을 ms 단위로 적어줍니다. TTFB 5.70s에서 이 값 5,664ms를 빼면 36ms가 남는데, 이게 네트워크 RTT + envoy 자체 오버헤드입니다.

### 1.3 결과

전체 5.91초 중 <strong>5.66초(95.8%)가 서버 처리 시간</strong>이었습니다. 네트워크 RTT는 36ms로 정상 범위였고, Content Download도 208.8ms(17.7MB/s)로 빠른 편이었습니다. 병목은 명확히 서버 안에 있었습니다.

여기서 한 가지 짚어둘 점이 있습니다. 현재 구조는 CSV + ZIP을 메모리에서 다 만든 다음 한 번에 응답을 시작하는 <strong>‘Full-buffer’ 안티패턴</strong>을 보이고 있습니다. 데이터 크기에 비례해 메모리가 급격히 증가하므로, 대규모 데이터를 전송해야 하는 API에는 부적절합니다. 이 부분은 Part2에서 다시 다루도록 하겠습니다.

  [그림] Full-Buffer vs Streaming
</Figure>

> 정리<br />응답이 느릴 때 가장 먼저 할 일은 TTLB/TTFB로 응답 시간을 분해하고, <strong>서버 사이드 처리 시간을 분리</strong>하는 것입니다. <br />envoy/istio 환경이라면 `X-Envoy-Upstream-Service-Time` , 아니라면 APM이나 서버 자체 로그를 활용해 네트워크와 서버를 갈라서 측정해야 합니다.

## 2. 구간 로깅 — 서버 내부를 단계로 가르기

### 2.1 무엇을 로그로 찍을 것인가?

서버 처리가 5.66초인 것 까지는 확인했습니다. 이제 서버 안에서 <strong>어느 메서드, 어느 단계가</strong> 병목인지 확인해야 합니다.

의심은 두 갈래였습니다. <strong>시간</strong>은 MongoDB aggregation일 가능성이 컸고, <strong>메모리</strong>는 CSV → ZIP 변환 파이프라인일 가능성이 컸습니다. 두 가지 의심을 한 번에 검증하려면 각 단계에서 <strong>시간과 힙 사용량</strong>을 동시에 봐야 했습니다.

그래서 핵심 경로의 각 단계에서 <strong>prefix + elapsed + heap</strong>을 확인하는 로그를 설계했습니다.

### 2.2 적용한 구간 로깅 패턴

1\. prefix는 의미 단위로 묶었습니다.

- `B` = <strong>B</strong>ulk fetch (MongoDB 대량 조회)
- `D` = <strong>D</strong>TO 변환
- `E` = <strong>E</strong>ncode / <strong>E</strong>xport (CSV 생성·인코딩)
- `Z` = <strong>Z</strong>ip (압축)

2\. elapsed는 해당 단계의 소요 시간을 ms로 측정했습니다.

3\. heap은 `ManagementFactory.getMemoryMXBean().getHeapMemoryUsage().getUsed()`로 그 시점의 힙 사용량을 함께 찍었습니다.

### 2.4 두가지 발견

<strong>시간 측면에서 MongoDB가 비효율적이었습니다.<br /></strong>B 단계가 4,653ms로 전체 처리의 78%를 차지했습니다. Mongo aggregation pipeline이 단 4,300건에도 이 정도 시간을 쓴다는 것은 운영 데이터가 늘면 비선형으로 폭증할 신호였습니다.

<strong>메모리 측면에서 CSV 단계부터 폭증이 시작됐습니다.<br /></strong>E1에서 한 번에 +191MB가 늘었고, E2에서 +89MB, Z1에서 +24MB가 추가되었습니다. 같은 데이터가 단계를 거치면서 총 7번 복제되었고, 그 사이 원본 List도 GC가 회수하지 못합니다. “데이터 전체가 한 번에 메모리에 있어야 한다"는 가정이 코드 전체에 깔려 있었던 셈입니다. 결국 입력 23.5MB가 866MB까지 35배 부풀었습니다.

<Figure src="/posts/ttlb-ttfb-download-api-bottleneck/09.png" alt="[그림] 7번 복사로 35배 힙 메모리 폭증" width={1258} height={1060}>
  [그림] 7번 복사로 35배 힙 메모리 폭증
</Figure>

elapsed만 찍었다면 단순히 MongoDB 조회부분만 고치면 되겠다고 생각할 수 있습니다. heap을 함께 찍었기 때문에 <strong>시간 병목과 메모리 병목이 다른 자리에 있다는 사실</strong>이 분리되어 보였습니다.

> 정리<br />의심이 여러 갈래일 때는 측정도 그 갈래만큼의 축으로 동시에 봐야 합니다.<br />prefix를 의미 단위로 붙이면 단계가 많아져도 로그를 풀어내기 쉽습니다.

## 3. 측정값을 환경으로 환원하기 — 컨테이너 한도와 데이터 규모

### 3.1 JVM 힙 한도 역산

Dockerfile에서 JVM 힙은 컨테이너 메모리의 70%로 잡혀 있었습니다.

```dockerfile
ENV JAVA_OPTS="-XX:+UseContainerSupport -XX:MaxRAMPercentage=70.0"
```

`MaxRAMPercentage=70.0`은 컨테이너 cgroup 메모리 한도의 70%를 JVM 최대 힙으로 사용하라는 옵션입니다. 고객사 배포 스펙의 memory limit은 4Gi였으니 힙 한도는 2.8GB 입니다.

### 3.2 데이터 규모별 위험도

4,300건 측정의 피크 866MB를 기준선으로 잡고, 컨테이너 메모리별 위험도를 추정하면 다음과 같습니다.

| 컨테이너 메모리 | JVM 힙 (70%) | 4,376건 점유율 | 추정 |
| --- | --- | --- | --- |
| 1 GB | 700 MB | \~123% | OOM 거의 확실 |
| 2 GB | 1.4 GB | \~62% | 데이터 2배면 OOM |
| **4 GB (고객사)** | **2.8 GB** | **\~31%** | **데이터 3\~4배면 OOM** |
| 8 GB | 5.6 GB | \~15% | 6\~7배까지 견딤 |

<p className="table-caption">[표] 데이텨 규모별 위험도 측정표</p>

4,300건은 약 2일치 채팅로그 수이며, 최대치는 3개월로 제한되어 있습니다. 어림잡아 18만 건으로 이번 측정치의 45배 수준입니다. 4GB 컨테이너 한도(2.8GB)를 한참 넘는 규모였습니다.

장애 시점에 운영 메모리 그래프를 직접 보지 못해도, 측정값과 환경 정보(컨테이너 한도 + 데이터 규모 비율)만으로 OOM 발생 가능성을 정량적으로 추정할 수 있습니다.

> 정리<br />측정값을 토대로 환경정보(컨테이너 한도, 데이터 규모, 트래픽 등)와 결합하여 운영 영향을 역산할 수 있습니다.

## 4. 정리 — 측정으로 진단한 두 가지 문제

측정 결과로 진단된 문제는 두 가지였습니다.

1. <strong>Mongo aggregation 쿼리의 비효율<br /></strong>Mongo aggregation pipeline이 4,300건 처리에 4,653ms를 썼고, 이는 전체 처리 시간의 78%였습니다. 운영 데이터 규모가 늘어나면 비선형으로 폭증할 신호였습니다.
2. <strong>CSV → ZIP 변환 파이프라인 다중 복사<br /></strong>같은 데이터가 단계별로 7번 복제되면서 입력 23.5MB가 힙 866MB(약 35배)까지 부풀었습니다. 데이터 양이 늘어날수록 힙은 선형으로 따라 늘어나는 구조였습니다.

진단에 따라 아래와 같은 해결방안이 도출되었습니다.

1. <strong>쿼리 최적화<br />aggregation pipeline 자체를 재설계해 시간 병목을 줄이는 것</strong>
2. <strong>stream 파이프라인</strong><br />데이터가 어디서든 한 번에 메모리에 통째로 올라가지 않도록, DB 조회부터 응답 전송까지 흐름을 끊지 않고 흘려보내는 것

채팅 로그 특성상 데이터 양이 계속 늘어나기 때문에 단순히 수직 확장으로 해결할 것이 아니라<strong> JVM heap peak가 데이터 규모와 무관하게 일정하게 유지되는 구조</strong>가 필요했습니다.

이번 글에서 다룬 측정 도구를 정리하면 다음과 같습니다.

- <strong>TTLB/TTFB + envoy 헤더</strong>: 응답 시간 분해, 네트워크, 서버 시간 측정
- <strong>구간 logging(prefix + elapsed + heap)</strong>: 서버 안에서 시간 병목과 메모리 병목 찾아내기
