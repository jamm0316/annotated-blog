2026년 4월, 인스타그램 계정 2만여 개가 탈취된 것으로 추정되는 사건이 있었다.

공격자는 메타의 AI 고객지원에 계정 복구를 요청해, 비밀번호 재설정 링크를 자기가 가진 메일 주소로 받아 냈다. 복구 과정에서 요청한 메일 주소가 계정에 등록된 주소와 같은지 제대로 확인하지 않아 벌어진 사건이었다.

  출처: BleepingComputer — Over 20,000 Instagram accounts stolen in Meta AI support hack
</Figure>

그런데 메타가 미국 메인주 법무장관실에 낸 신고서에는 이런 내용이 있었다. “공격자는 계정 주인이 2단계 인증을 켜 두지 않은 경우에 로그인할 수 있었다.” 비밀번호를 바꿀 수 있게 된 공격자도, 2단계 인증이 켜진 계정에서는 그다음으로 넘어가지 못한 것으로 보인다.

국내에서도 KT, SK텔레콤, 쿠팡, 신한은행 등 보안 문제가 계속해서 발생하고 있다. 여러 사이트에서 하나의 비밀번호를 돌려 쓰는 경우가 많아 한 곳에서 유출되면 다른 곳에 대입해 볼 수 있는 문제까지 생긴다.

우리 서비스에 2단계 인증을 붙인 계기는 금융권 고객사의 요구였다. 하지만 위 사건들을 보면 금융권이 아니어도 계정을 다루는 서비스라면 갖춰야 할 기능이라고 생각한다.

신한은행 앱에 로그인하면 자동 로그인을 설정해 둬도 인증 코드를 한 번 더 묻는다. 번거롭지만 이유가 있다. 비밀번호가 유출되더라도 내 휴대폰까지 가진 사람은 드물고, 인증서 비밀번호까지 아는 사람은 더욱 드물기 때문이다.

<Figure src="/posts/two-factor-auth-design/03-bank-app-pin.png" alt="은행 앱이 인증서 비밀번호 6자리를 묻는 화면" width={1125} height={900} />

인증 수단은 크게 3가지로 나눌 수 있다.

- 아는 것(Know): 비밀번호, PIN
- 가진 것(Have): 인증 앱, 메일, 보안 키
- 나 자신(Are): 지문, 얼굴, 홍채

2FA(Two-Factor Authentication, 2단계 인증)는 이 중 서로 다른 부류를 함께 확인하는 것이다. 만약 모두 확인하게 된다면 3단계 인증이 된다.

<Figure src="/posts/two-factor-auth-design/04-auth-factors.png" alt="아는 것·가진 것·나 자신 세 원이 겹치는 벤 다이어그램. 우리 서비스는 비밀번호(아는 것)와 이메일 코드 또는 인증 앱 코드(가진 것)를 확인한다" width={1400} height={1240} />

## 2차 인증 수단 고르기

우리 서비스는 비밀번호로 1차 인증만 하고 있었다. 그렇다면 2차 인증은 무엇으로 하면 좋을까?

OTP처럼 대부분 별도의 인프라를 구축하고 하드웨어를 갖춰야 하는 방안은 제외했다. 따라서 2FA는 아는 것 + 가진 것으로 진행하기로 정했다.

가진 것을 확인하는 방식은 아래와 같다.

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| SMS | 설치 없이 바로 받을 수 있다 | 전송 지연, 문자 가로채기 위험 |
| 이메일 | 설치 없이 바로 받을 수 있다 | 메일 계정이 탈취되면 함께 뚫린다 |
| 인증 앱 (TOTP) | 인터넷 연결 없이 앱에서 코드를 만든다 | 앱을 설치해야 한다 |
| 하드웨어 토큰 | 독립된 장치라 보안성이 높다 | 장치 비용이 든다 |

이 중 인증 앱이 쓰는 TOTP(Time-based OTP)도 OTP의 한 종류다. 다만 코드를 만드는 것은 사용자의 휴대폰에 설치한 인증 앱이라, 하드웨어와 인프라를 우리가 직접 제공하지 않아도 된다.

서버와 앱이 같은 비밀키를 나눠 갖고, 현재 시각을 30초 단위로 자른 값과 비밀키를 HMAC-SHA1로 계산해 6자리 숫자를 만든다. 서버도 같은 계산을 해서 두 숫자가 같으면 통과시킨다.

카운터를 쓰는 HOTP는 서버와 앱의 카운터가 어긋나면 다시 맞춰야 하지만, TOTP는 시각을 쓰므로 시계만 맞으면 된다. 대신 서버와 휴대폰의 시계가 어긋나면 인증에 실패한다.

실제 서비스는 어떻게 하는지 보려고 GitHub에 직접 인증 앱을 등록해 봤다. GitHub은 인증 앱, SMS, 패스키, 보안 키를 지원하고, SMS보다 인증 앱을 쓰라고 권장한다.

<Figure src="/posts/two-factor-auth-design/05-github-2fa-methods.png" alt="GitHub 2단계 인증 설정 화면. SMS 항목에 Less secure 표시와 함께 인증 앱을 쓰라는 안내가 있다" width={1400} height={944} />

설정 화면에서 인증 앱 추가를 누르면 QR 코드가 뜬다. Google Authenticator로 QR을 스캔하고, 앱에 뜬 6자리 코드를 한 번 입력하면 등록이 끝난다.

<Figure src="/posts/two-factor-auth-design/06-github-totp-setup.png" alt="GitHub 인증 앱 등록 화면. QR 코드와 앱에서 받은 코드를 입력하는 칸이 있다" width={932} height={545} />

이후 로그인할 때는 비밀번호 다음에 2FA 창이 뜨고, 앱의 6자리 코드를 입력하면 로그인이 끝난다. GitHub이 제공한 것은 QR 코드와 코드 검증뿐이었고, 코드를 만드는 일은 내 휴대폰의 Google Authenticator앱을 이용했다.

우리 등록 흐름도 이 순서를 따랐다. QR을 발급한 시점에는 대기 상태로 두고, 첫 코드 검증이 성공해야 활성화한다.

## 설계에서 고려해야 할 것

요구사항은 네 가지였다.

- 관리자가 전역 정책을 정한다. 2FA 사용 여부, 인증 앱 허용 여부, 강제 적용과 선택 적용 중 하나
- 이메일 인증은 항상 켜져 있고 누구도 끌 수 없다
- 사용자는 수단을 고르지 않는다. 선택 적용일 때 2FA 사용 여부, 인증 앱이 허용될 때 인증 앱 사용 여부만 정한다
- 인증 앱을 잃어도 사용자가 스스로 복구할 수 있어야 한다

여기에 나는 두 가지 경우를 실패로 봤다.

- 2차 인증을 거치지 않고 서비스에 들어오는 길이 하나라도 남는 것.
- 정상 사용자가 스스로 빠져나올 수 없게 잠기는 것.

따라서 아래 3가지를 설계 핵심 포인트로 봤다.

- 1차 인증과 2차 인증 사이에서 무엇으로 요청을 막을까?
- 관리자 정책과 개인 선택이 겹칠 때 다음 화면을 어떻게 정할까?
- 이미 로그인한 사용자가 2FA 설정을 바꿀 때 무엇으로 본인을 확인할까?

전체 구조는 아래와 같다. 로그인 경로에는 필터와 판정 서비스가 있고, 설정을 바꾸는 경로에는 재인증 관문과 기능별 서비스가 있다.

<Figure src="/posts/two-factor-auth-design/07-structure.png" alt="PreAuthFilter 가 로그인 경로에서 NextStepResolver 로 이어지고, NextStepResolver 는 GlobalPolicy·UserChoice·AppCredential 을 읽는다. ReEnrollService·AppRevokeService·TwoFactorDisableService 는 ReauthVerifier 를 거친다" width={1400} height={1016} />

## 2차 인증 전용 토큰 만들기

기존 로그인은 1차 인증이 끝나는 순간 정식 액세스 토큰을 발급했다. 이 상태에서 2FA 화면만 띄우면, 사용자는 이미 유효한 토큰을 가지고 있으니 화면을 건너뛰고 API를 직접 호출할 수 있다.

그래서 1차 인증 직후에는 2차 인증에만 쓸 수 있는 pre-auth 토큰을 발급하도록 설계했다. 2차 인증을 통과하면 정식 토큰으로 교환한다. 정책이 꺼져 있거나 사용자가 2FA를 쓰지 않기로 했다면 pre-auth 토큰 없이 바로 정식 토큰을 주도록 설계했다.

문제는 pre-auth 토큰을 어디서 알아보고 막느냐였고, 서비스 안의 필터에서 막도록 했다. 필터는 `PRE_AUTH` 권한을 가진 요청이 허용 목록에 있는 2FA API가 아니면 모두 거부한다. 앞단의 API 게이트웨이는 토큰을 검증할 때 호출 경로를 알 수 없어, 경로별로 막을 수 없었기 때문이다.

허용 목록에는 로그인을 마치는 데 필요한 2FA API만 넣었다. 인증 앱 해제나 2FA 해제처럼 설정을 바꾸는 API는 목록에서 빼서, 2차 인증을 마치기 전에는 호출할 수 없게 했다. 다만 필터가 빠지면 pre-auth 토큰이 모든 API를 통과하므로, 필터의 존재와 순서를 테스트로 고정했다.

## 사용자 상태를 하나의 판정으로 모으기

다음 화면을 정하는 데 필요한 값은 셋이다. 관리자 정책, 개인 선택, 인증 앱 등록 상태. 이 조합에 따라 사용자는 바로 로그인하거나, 2FA 사용 여부를 묻는 화면, 인증 앱 등록을 권하는 화면, 인증 앱 등록 화면, 인증 앱 코드 입력 화면, 이메일 코드 입력 화면 중 하나를 선택한다.

<Figure src="/posts/two-factor-auth-design/08-next-step.png" alt="1차 인증 성공 뒤 전역 정책, 적용 방식, 개인 2FA 선택, 인증 앱 허용, 개인 인증 앱 선택, 등록 완료 여부에 따라 정식 토큰 발급·이메일 코드 입력·인증 앱 등록·인증 앱 코드 입력 중 하나로 가는 흐름도" width={1400} height={2959} />

이 판단을 판정 서비스 하나에 모았다. 판정 서비스는 다음 단계를 돌려주고, 프론트는 그 값만 보고 화면을 렌더링한다.

<NextStepPlayground caption="값을 바꾸면 판정 서비스가 돌려줄 다음 단계가 바뀐다. 분기는 위 흐름도와 같다." />

등록·검증 API도 같은 판정을 거쳐 지금 단계가 아닌 요청은 거부한다. 이메일 인증 대상인 사용자가 pre-auth 토큰으로 인증 앱 등록 API를 호출해, 원하는 인증 앱을 붙여 2차 인증을 우회하는 길을 막기 위해서다.

## 재인증은 무엇으로 해야 할까?

로그인한 뒤에도 본인을 다시 확인해야 하는 조작이 있다. 인증 앱 재발급, 인증 앱 해제, 2FA 해제다. 계정의 2FA 구성 자체를 바꾸는 조작이라, 액세스 토큰만으로 허용하면 토큰을 탈취한 사람이 2FA를 끌 수 있다.

처음에는 비밀번호와 2차 요소를 함께 받았다. 그런데 SSO로 가입한 계정에는 비밀번호가 없다. 비밀번호 유무로 분기하는 방법을 넣었지만, 프론트는 로그인 단계에서 계정 유형을 알 수 없어 비밀번호 입력칸을 렌더링할 분기를 찾을 수 없었다. 같은 버튼이 계정마다 다르게 동작했다. 결국 기획이 재인증에서 비밀번호를 빼고 기능별로 2차 요소를 고정하기로 확정했다.

남은 질문은 인증 앱 코드와 이메일 코드 중 무엇을 언제 요구하느냐였다. 두 요소는 강도가 다르다. 인증 앱은 기기에 저장된 비밀값으로 코드를 만들고 네트워크를 타지 않는다. 메일함은 다른 서비스의 비밀번호 하나로 열린다. 리서치에서 이메일 방식의 약점으로 본 것도 메일 계정 탈취였다. 그래서 조작이 강한 요소를 없애는지, 새로 만드는지를 기준으로 정했다.

| 조작 | 받는 요소 | 이유 |
| --- | --- | --- |
| 인증 앱 해제 | 인증 앱 코드만 | 이메일로 인증 앱을 없애면 이후 로그인이 이메일만으로 통과해, 계정 보안이 약한 요소 수준으로 내려간다 |
| 인증 앱 재발급 | 인증 앱 코드 또는 이메일 코드 | 기기를 잃은 사용자의 복구 경로다. 등록 확인 전까지 기존 인증 앱이 유지되므로 이메일로 열어도 그 순간 계정이 약해지지 않는다 |
| 2FA 해제 | 인증 앱이 있으면 인증 앱 코드, 없으면 이메일 코드 | 해제는 인증 앱까지 함께 지운다 |

인증 앱을 잃은 사용자가 2FA를 끄려면 이메일로 재발급해 새 인증 앱을 등록한 뒤, 그 코드로 해제한다. 두 단계지만 각 단계가 같은 기준을 지킨다.

비밀번호가 빠지면서 재인증이 확인하는 요소는 하나로 줄었다. 그래서 강한 요소를 없애는 조작에는 인증 앱 코드만 받도록 기준을 좁게 잡았다.

### 재인증 실패 횟수 제한하기

재인증은 6자리 코드 하나로 계정의 2FA 설정을 바꿀 수 있게 한다. 코드를 무제한으로 넣어 볼 수 있다면 언젠가는 맞힐 수 있으므로, 실패가 5번 쌓이면 10분 동안 재인증을 막도록 했다. 이 실패 횟수는 로그인 실패 횟수와 따로 센다. 하나로 세면 로그인 실패가 재인증을, 재인증 실패가 로그인을 잠그기 때문이다.

## TOTP 라이브러리와 직접 구현의 경계

TOTP 계산은 RFC 6238에 정해져 있어 직접 구현할 수도 있었다. 하지만 암호 계산을 직접 짜면 그 코드가 맞는지 검증하고 리뷰하는 부담이 크고, 일정에도 위험이 된다. 따라서 계산은 검증된 라이브러리에 맡기기로 했다.

후보는 두 개였다.

| 후보 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| googleauth | 참고 자료가 많고, 비밀키 생성·검증·등록용 URI 생성을 모두 제공한다 | 유지보수가 활발하지 않다 | 채택 |
| samstevens totp | 비교적 최근 라이브러리이고 Spring과 잘 맞는다 | 사내 사용 이력이 없다 | 문제가 생기면 전환 |
| RFC 6238 직접 구현 | 외부 의존이 없다 | 암호 코드를 직접 검증해야 하는 부담이 크다 | 제외 |

나는 googleauth를 골랐다. 라이브러리에 맡길 것은 계산뿐이라, 기능이 많은 쪽보다 필요한 기능만 있고 참고 자료가 많은 쪽이 낫다고 봤다. 다만 유지보수가 활발하지 않다는 위험은 남는다. 그래서 문제가 생기면 samstevens totp로 바꾸기로 했다. 라이브러리를 계산에만 쓰기 때문에, 바꾸더라도 고칠 곳은 계산 부분에 그칠 것이라고 생각했다.

이름에 Google이 붙어 있지만 특정 앱에 묶이지는 않는다. 라이브러리가 만드는 등록용 URI는 인증 앱들이 공통으로 읽는 표준 형식이라, Google Authenticator뿐 아니라 Microsoft Authenticator나 Authy로도 등록할 수 있다. 다만 등록용 URI 대신 종료된 Google Chart API의 이미지 주소를 돌려주는 메서드가 있어 그 메서드는 쓰지 않았고, QR 이미지는 프론트에서 그리도록 했다.

라이브러리에는 코드 계산만 맡기고, 검증 정책과 상태, 저장은 직접 다뤘다. 상태와 정책까지 라이브러리에 맡기면 통제할 수 없기 때문이다. 실제로 라이브러리의 검증 메서드는 맞았는지 여부만 돌려줘서 어느 시간 구간의 코드가 맞았는지 알 수 없다. 그러면 이미 쓴 코드를 다시 쓰는 재사용을 막을 수 없다. 라이브러리가 비밀키 저장까지 대신해 주는 기능도 쓰지 않았다. 비밀키는 암호화해서 저장해야 하고, 그 방식은 우리가 정해야 하기 때문이다.

## 2단계 인증을 설계하며 배운 것

2FA 화면을 띄우는 것과 2FA를 강제하는 것은 다르다. 사용자가 화면을 건너뛰고 API를 직접 부를 수 있는 이상, 2차 인증을 마쳤는지는 서버가 요청마다 확인해야 한다. pre-auth 토큰과 허용 목록, 단계 판정이 이 문제를 해결해준다.

또한 로그인만 막는다고 계정이 보호되지 않는다. 도입에서 본 인스타그램 사건도 로그인이 아니라 계정 복구 과정에서 일어났다. 인증 수단을 해제하거나 다시 등록하는 수단에 보안이 약하면, 공격자는 로그인 대신 그쪽으로 들어온다.

그래서 재인증에서도 2차 요소를 받도록 했다. 같은 가진 것(Have)이라도 인증 앱과 메일함은 강도가 다르고, 약한 요소로 강한 요소를 없앨 수 있게 두면 계정의 보안은 결국 가장 약한 요소 수준으로 내려간다고 생각한다.

인증 앱 코드는 현재 시간 구간 하나만 허용했다. 휴대폰 시계가 30초 이상 어긋나면 코드가 맞아도 통과하지 못한다. 운영에서 이런 실패가 얼마나 나오는지 보고 허용 범위를 다시 정해 봐야겠다.
