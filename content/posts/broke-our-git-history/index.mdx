### Our Team’s Git Management Philosophy

Our team maintains a strict approach to Git history management: we prioritize linear, traceable commit history. Each pull request is clearly delineated by merge commits, and every commit should represent a meaningful unit of change. This discipline is essential for debugging — when issues arise, we need to identify precisely where things went wrong.

While I had prior experience with Git through personal projects, my knowledge was superficial — limited to basic pull, push, and merge operations. I lacked a fundamental understanding of version control principles. This incident demonstrates the significant risks that arise when developers use tools without understanding the underlying mechanics. I hope sharing this experience prevents others from making similar mistakes.

### First Mistake: One Wrong Button Click

I submitted a PR containing four carefully organized commits. I had already squashed six commits down to four locally and crafted clear commit messages. After code review approval, all that remained was merging into the main branch.

Without thinking, I clicked the green button on the GitHub PR interface.

For some reason, the default option was set to “Squash and merge.”

<Figure src="/posts/broke-our-git-history/01.png" alt="" width={948} height={732} />

I only realized my error after checking the Git log. The four commits I had meticulously structured were now collapsed into a single commit. My carefully planned progression — implementation → refactoring → review feedback — had been compressed into one line of history. Additionally, our previously linear history was now distorted.

<Figure src="/posts/broke-our-git-history/02.png" alt="" width={2048} height={588} />

### Second Mistake: Attempting Recovery Without Understanding

I posted in the team channel: “I made a mistake with the merge. I’ll revert it.” Then I began attempting recovery:

```bash
git checkout main
git pull origin main
git checkout feature/api-key-status
git merge main
git push
```

I assumed this would work. However, during this time, another team member’s commits had been added to main. I proceeded with the merge without checking the Git log first.

In retrospect, this was an extremely dangerous decision from a development perspective. I was executing commands without understanding their purpose or anticipating the consequences.

The result:

```bash
Your branch and 'origin/main' have diverged,
and have 5 and 2 different commits each, respectively.
```

<Figure src="/posts/broke-our-git-history/03.png" alt="" width={1524} height={396} />

The history was now tangled. The feature branch was based on an older version of main, while main had progressed independently. The two branches had diverged.

## Complete Rollback and the Correct Approach

At this point, our team lead intervened.

“Let’s roll everything back.”

He performed a complete rollback of main to the state before the squash merge:

```bash
git checkout main
git reset --hard <commit-before-squash-merge>
git push --force origin main
```

A notification went out to the entire team:<br />“Main branch has been rolled back. Please pull the latest changes.”<br />My mistake had impacted the entire team. I felt genuinely apologetic.

At this point, I needed to clearly identify:

- <strong>The problem to solve</strong>: Maintain linear, traceable Git history
- <strong>What I didn’t understand</strong>: How Git commands operate and what “linear management” truly means
- <strong>The solution</strong>: Understand the underlying mechanics of each command and learn the correct procedures

I learned the following workflow:

```bash
# 1. Fetch latest from remote
git fetch origin

# 2. Switch to feature branch
git checkout <feature-branch>

# 3. Rebase - Critical step
git rebase origin/main

# 4. Force push with safety check
git push --force-with-lease origin <feature-branch>
```

After reviewing the log again, everything was correct. The merge commit clearly marked the feature’s boundaries, and all four commits were preserved in the history.

<Figure src="/posts/broke-our-git-history/04.png" alt="" width={800} height={160} />

### Analyzing My Mistakes

<strong>The Pitfall of Squash Merge<br /></strong>Squash merge creates clean history by consolidating commits like “WIP,” “fix again,” or “final commit (really)” into a single, meaningful commit. However, problems arise when you squash commits that were already meaningfully organized. My four commits represented distinct phases: <br />1. Implementation <br />2. Modifications <br />3. Review feedback <br />4. Documentation updates

After squashing, all context is lost. If a bug originated in step 2, your only options are reverting everything or keeping everything — granular rollback becomes impossible.

<strong>Why Rebase is Essential <br /></strong>This is precisely where my recovery attempt failed.

<strong>Without rebase</strong>, merging places your feature branch on top of an outdated main:

Scenario: While you’re working, a teammate commits to main

```text
main:    [C1] - [C2] - [C4(team)]
                  ↓
feature: [C1] - [C2] - [F1] - [F2]
                  ↑ Branched off here
```

Merging in this state can cause conflicts and create complex history.

<strong>Rebase</strong> repositions your work on top of the latest main: <br />After rebase:

```text
main:    [C1] - [C2] - [C4(team)]
                         ↓
feature: [C1] - [C2] - [C4] - [F1'] - [F2']
                                ↑ Go to the latest rebase
```

Now merging is clean, history remains linear, and conflicts are resolved locally beforehand.

<strong>The </strong>`-- no-ff`<strong> Flag: Preserving Merge History </strong><br />“Create Merge Commit” operates with the`--no-ff` option by default, which means “don’t fast-forward.” <br />Fast-forward is Git’s intelligent behavior, but it doesn’t create a merge commit:

<strong>Without </strong>`--no-ff`<strong>:</strong>

```text
main: [C1] - [C2] - [C4] - [F1] - [F2]
                     ↑ Where does the feature start/end?
```

<strong>With</strong>`--no-ff`<strong>:</strong>

```text
main: [C1] - [C2] - [C4] - [Merge]
                       ↓        ↑
                     [F1] - [F2]
```

Merge commits make feature boundaries explicit: “This feature started here and ended here.” They correspond 1:1 with PRs, and rollbacks become simpler — just revert the merge commit.

### Lessons Learned: The Right Way to Achieve Your Goals

I knew Git commands. I could pull, merge, and push. But I didn’t understand the fundamental problem Git was designed to solve or how its features should be used to achieve our objectives. I only knew surface-level operations.

After two failures, I realized:

<strong>Understanding technology properly means understanding not just what it does, but why it works that way.</strong>

Only then can you make informed decisions about how to achieve your goals.

### Pre-Merge Checklist

Now I always verify before merging:

1. Did I update main? (`git pull origin main`)
2. Did I rebase my feature on latest main? (`git rebase main`)
3. Did I use `--no-ff`? (`git merge --no-ff`)
4. Did I review the log? (`git log --graph`)

### Conclusion

Git is a powerful tool, but with great power comes the potential for equally powerful mistakes.

I learned two critical lessons:

<strong>First, corrupted history is difficult to recover.</strong> One squash merge eliminated four commits instantly.

<strong>Second, developers must understand their tools before using them.</strong> Operating on intuition outside of experimental environments introduces significant risk.

I hope this serves as a cautionary tale for others facing similar challenges.

### 완전 롤백, 그리고 정석대로

이 시점에서 팀장님이 개입하셨습니다.<br />“일단 다 되돌리자"<br />팀장님은 Squash merge 이전 시점으로 main을 완전히 되돌리셨습니다.

```bash

git reset --hard <squash-merge-이전-commit>
git push --force origin main
```

그리고 팀원 전체에게 공지가 갔습니다.<br />“Main 브랜치 롤백했으니 pull 다시 받으세요.”<br />나 때문에 팀원들이 피해를 받고 있었습니다. 정말 미안했습니다.

이 시점에서 저는 명확히 해야 했습니다.

- <strong>해결하려는 문제</strong>: Git log를 선형적이고 추적 가능한 상태로 관리
- <strong>내가 모르는 것</strong>: Git 명령어가 어떤 작업을 수행하는지, 선형 관리가 정확히 무엇인지
- <strong>해결 방법</strong>: 각 명령어의 동작 원리를 이해하고, 올바른 절차를 익히기

그리고 다음과 같은 절차를 배웠습니다.

```bash

# 2. Feature 브랜치로 이동
git checkout <작업 브랜치>

# 3. Rebase - 핵심!
git rebase origin main

# 4. Force Push
git push --force-with-lease origin <작업 브랜치>
```

그리고 다시 로그를 확인 했습니다.

이번엔 제대로 했습니다. 로그를 확인하니 Merge commit이 feature의 경계를 명확히 표시하고, 4개 커밋 히스토리가 모두 보존되어 있었습니다.

### 나의 실수 돌아보기

1. <strong>Squash Merge의 함정<br /></strong> Squash Merge는 히스토리를 깔끔하게 만들어줍니다. <br />“WIP 커밋”, “다시 커밋”, “진짜 마지막” 같은 의미 없는 커밋들을 하나로 정리할 때 유용하죠. <br />하지만 이미 로컬에서 의미 있게 나눈 커밋들까지 합치면 문제가 생깁니다. <br />저는 4개 커밋을 이렇게 나눴습니다:<br />1. 구현<br />2. 수정<br />3. 리뷰 반영 <br />4. 문서 업데이트 <br />Squash하면 이게 전부 하나가 됩니다. 나중에 2번 단계에서 버그가 생겼다면? <br /><strong>전체를 되돌리거나, 전체를 유지하거나 둘 중 하나만 가능</strong>합니다.
2. <strong>Rebase를 왜 해야 하나<br /></strong> 제가 복구를 실패한 이유가 바로 여기에 있습니다.<br /> Rebase 없이 merge하면 feature가 오래된 main 위에 있게 됩니다<br /><strong>상황: 내가 작업하는 동안 팀원이 main에 커밋</strong>

```text
main:    [C1] - [C2] - [C4(팀원)]
                  ↓
feature: [C1] - [C2] - [F1] - [F2]
                  ↑ 여기서 분기했음
```

이 상태로 merge하면 충돌이 날 수 있고, 히스토리가 복잡해집니다. Rebase는 작업을 최신 main “위로" 옮기는 작업입니다.

Rebase 후:

```text
main:    [C1] - [C2] - [C4(팀원)]
                         ↓
feature: [C1] - [C2] - [C4] - [F1'] - [F2']
                                ↑ 최신 base 위로 이동
```

이제 merge하면 깔끔합니다. 선형 히스토리가 유지되고, 충돌도 로컬에서 미리 해결할 수 있죠.

<strong>4. </strong>`--no-ff`<strong> : Merge의 흔적을 남긴다.</strong>

Create Merge Commit은 기본적으로`--no-ff `옵션으로 작동합니다.<br />이는 “Fast-forard 하지마"라는 뜻입니다.<br />Fast-forward는 Git이 똑똑하게 동작하는 방식인데, 문제는 Merge commit이 생기지 않는다는 겁니다.

<strong>— no-ff 없이:</strong>

```text
main: [C1] - [C2] - [C4] - [F1] - [F2]
                     ↑ feature가 어디서 시작/끝?
```

<strong>— no-ff 사용:</strong>

```text
main: [C1] - [C2] - [C4] - [Merge]
                       ↓        ↑
                     [F1] - [F2]
```

Merge commit이 있으면 “이 기능은 여기서 시작해서 여기서 끝났다"가 명확해 집니다. <br />PR과 1:1로 대응되고, 롤백할 때도 Merge commit 하나만 되돌리면 됩니다.

### 배운 것: 목표를 이루는 올바른 방법

저는 Git 명령어를 알고 있었습니다. Pull도 하고, Merge도 하고, Push도 했죠.

하지만 내가 Git이라는 도구를 통해서본질적으로 어떤 문제를 해결하고자 하는지, 그리고 각 기능들을 활용해서 어떻게 목표를 달성하는지 알지 못했습니다. <br />표면적인 사용법만 알았던 거죠.

두번의 실패 끝에 깨달은 건 이겁니다.<br />기술을 제대로 이해한다는 건, <br />그 기술이 무엇을 하는지가 아니라 왜 그렇게 동작하는지를 이해하는 것입니다.

그래야 목표를 이루기 위해 어떤 행동을 해야하는지 판단할 수 있습니다.

### 체크리스트

이제는 Merge전에 항상 확인합니다.<br />1. Main 최신화 했나?(git pull origin main)<br />2. Feature를 최신 main 위로 올렸나?(git rebase main)<br />3. — no-ff 붙였나?(git merge — no-ff)<br />4. 로그 확인했나?(git log — graph)

### 마치며

Git은 강력한 도구입니다. 하지만 강력한 만큼 실수도 강력하게 돌아옵니다.<br />저는 이번에 두 가지를 배웠습니다.

첫째, <strong>히스토리는 한 번 망가지면 복구가 어렵습니다.<br /></strong> Squash merge 한 번에 4개의 커밋이 날아갔습니다.

둘째, <strong>개발자는 도구를 알고 사용해야 합니다.<br /></strong> 감으로 사용하는 것은 실험 환경이 아닌 이상 엄청난 리스크를 초래할 수 있습니다.
