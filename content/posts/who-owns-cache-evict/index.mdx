이전 글에서 [캐시를 붙이기 전에 고려해야할 3가지 질문](https://medium.com/@evanbackeng/%EC%BA%90%EC%8B%9C%EB%A5%BC-%EB%B6%99%EC%9D%B4%EA%B8%B0-%EC%A0%84%EC%97%90-%EB%AC%BC%EC%97%88%EC%96%B4%EC%95%BC-%ED%95%A0-%EC%84%B8-%EA%B0%80%EC%A7%80-%EC%A7%88%EB%AC%B8-4f50548001b0?sharedUserId=evanbackeng)에 대해 정리했다. 그 기준으로 그룹 트리 조회 API에 Redis 캐시를 붙였고, 응답 시간을 376ms에서 101ms로 줄였다.

캐시를 도입하고 나니 이를 안정적이게 운용하려면 고려해야할 것이 또 있었다. 캐시는 근본적으로 데이터 저장을 이원화 하는 것이다. 따라서 아래 두가지를 반드시 고려해야 했다.

1. 원본 데이터가 변경되면 캐시를 어떻게 갱신할 것인가?
2. 캐시가 만료되고 갱신되기 전에 요청이 몰린다면 모두 원본을 조회할 텐데 이럴때 비효율은 어떻게 대응할 것인가?

이번 글에서는 1번 Cache Evict에 대해서 다룬다. 2번은 cache stampede라고 부르는데, 캐시보다 동시성 제어에 가까운 주제라 다음 글에서 따로 다룬다.

## 1. cache evcit란 무엇인가

캐시는 성능 최적화를 위해 데이터를 원본과 사본으로 나누는 비용을 치러야한다. 데이터를 이렇게 이원화하면 원본 데이터에 CUD가 발생할 경우 두 데이터를 계속 최신화하여 동기화를 맞춰줘야 한다. 따라서 기존 캐시를 지우는 동작을 고려해야 하고, 이를 Cache Evict라고 한다.

evict는 “(주택이나 토지에서 법적으로) 쫓아내다"라는 뜻이다. 기존에 등록된 캐시를 지우고(쫓아내고) 다음 read때 캐시를 재등록하는 것이다. 따라서 캐시 evict이후에 최초로 캐시를 등록하는 API를 호출하는 사용자는 호출 시간이 다른 사용자에 비해 조금 느릴 수 있다.

### 1.1 처음에는 서비스 계층에 두었다

cache evict를 비즈니스 로직이라 판단하고 service 계층에 두었다. “이 데이터가 바뀌었으니 캐시를 버려야한다"는 판단은 도메인 판단이라고 보았고, 도메인 흐름을 아는 서비스가 이 책임을 가져가야한다고 생각했다.

```java
@Service
public class AuthGroupService {

    @CacheEvict(cacheNames = "groupTree", allEntries = true)
    public void save(GroupRequest request) {
        authGroupDataAdapter.createGroup(request);
    }
}
```

그러다보니 팀원 전부가 그룹 정보가 캐싱되고 있다는 컨벤션을 기억하고 있어야했다. 이를 깜빡하고 그룹 CUD에 evict를 붙이지 않는다면, 기존 캐시 데이터가 지워지지 않으므로 운영 환경에서 변경된 정보가 반영되지 않았다.

실제로 SSO 로그인 과정에서 그룹을 자동 생성하는 경로에 evict가 빠져 있었고 그룹을 생성하는 API도 evict를 사용하고 있지 않았다. 기억에 의존하는 정책의 위험함이라는 생각이 들었다.

### 1.2 누구에게 책임이 있나?

나는 모두가 캐시 컨벤션을 기억해야하는 정책은 위험하다 판단했다. 사람의 기억보다 강력한 정책이 필요하다 생각했다. 그래서 질문을 바꿨다.

- “어느 계층에 둬야 의도가 드러나는가" → 개발자가 의도를 드러내고, 다른 개발자가 그것을 읽어야 정책이 유지 된다.
- “원래 이 로직의 책임은 누구의 것인가" → 객체가 자기 책임을 스스로 수행한다.

후자가 OOP에도 부합하는 선택이였다. Cache Evict가 필요한 이유는 DB에 쓰기가 일어났기 때문이다. 즉, 데이터가 실제로 바뀌는 지점은 DB에 접근하는 쪽이였다.

### 그렇다면 Repository가 아니라 왜 DataAdapter에 책임을 줬나?

여기서 한 가지를 더 고민했다. DB에 직접 접근하는 것은 repository이니, 더 깊은 repository에 두는 것이 우회를 막기에 더 좋지 않을까?

하지만 이 논리를 끝까지 밀면 repository도 아니고 DB레벨까지 가게된다. 그래서 아래 3가지 기준을 가지고 판단했다.

1. <strong>내가 소유한 코드인가?<br /></strong>repository는 Spring Data가 구현을 생성해주는 인터페이스이고, 여러 어댑터가 함께 쓰는 공용 자원이다. 여기에 groupTree라는 특정 캐시 이름을 적으면 범용 저장소 인터페이스가 특정 캐시에 강하게 결합된다. 나중에 다른 캐시가 같은 repository를 쓰기 시작하면 이름이 계속 늘어날 수 있었다.
2. <strong>바깥에서 도달 가능한 가장 바깥의 강제 지점인가?<br /></strong>포트/어댑터 구조에서 repository는 이미 어댑터의 내부 구현이다. 즉 어댑터를 통과하지 않고 repository에 닿을 방법이 없다.
3. <strong>논리적 쓰기 한 번에 대응하는 단위인가?<br /></strong>repository 메서드는 save, delete 같은 원자적 연산이다. 어댑터 메서드 하나가 repository를 세 번 호출하면 evict도 세 번 일어난다. “그룹 하나를 생성했다"라는 사건에 대응하는 단위는 어댑터 쪽이다.

그래서 기존 서비스에 선언되어 있던 evict 로직을 dataAdapter의 CUD로직으로 옮겼다.

```java
@Component
public class AuthGroupDataAdapter {

    @CacheEvict(cacheNames = "groupTree", key = "'ALL'")
    public AuthGroup createGroupEntityWithName(String name) {
        // 실제 쓰기가 일어나는 지점
    }
}
```

책임을 dataAdapter로 옮기자 group CUD를 진행하던 로직들은 반드시 dataAdapter를 거치게 되었고 앞으로 새로운 경로가 생기더라도 cahce evict는 개발자의 기억에 의존하지 않아도 됐다.

### 1.3 캐시 이름 전체를 비울 것인가, 항목 하나를 지울 것인가

evict를 옮기면서 최적화를 고려했다.

스프링 캐시는 두 층으로 나뉜다. `CacheManager`가 이름별로 `Cache`를 관리하고, 각 `Cache`가 key-value를 담는다. 그래서 `@CacheEvict`에는 캐시 이름과 항목 키를 따로 지정할 수 있고, 지우고 싶은 캐시를 정밀하게 설정할 수 있다.

Redis에서 이 캐시 이름이 키의 접두사가 된다.

```text
@Cacheable(cacheNames = "groupTree", key = "'ALL'")
                            ↓             ↓
        Redis 키:      groupTree   ::   ALL
```

`@CacheEvict` 의 선언 중 `allEntries=true` 는 `groupTree::` 로 시작하는 키 전부를 지우라는 뜻이다. 만약 Redis에 이런 접두사를 Map처럼 묶어두는 자료구조가 있었다면 O(1)로 빠르게 해결됐을 것이다. 그러나 이러한 자료구조가 없기에 `RedisCache.clear()`는 `groupTree::*` 패턴으로 키 스페이스를 전체 조회한 뒤 찾은 것을 지운다. 따라서 `allEntries=true`선언은 O(N) 연산이 된다.

더구나 이번 캐시는 항목이 `groupTree::ALL` 하나 뿐이라 전체 조회로 얻는 것이 전혀 없었다. 그래서 지울 키를 하나로 특정해 O(1) 삭제로 바꿨다.

```java
// Before — 패턴 스캔 O(N)
@CacheEvict(cacheNames = "groupTree", allEntries = true)

// After — 단건 삭제 O(1)
@CacheEvict(cacheNames = "groupTree", key = "'ALL'")
```

여기서 키를 적을 때 주의해야 할 점이 있다. `cacheNames = “groupTree”` 까지는 문자열(literal)이지만 `key = “‘ALL’”` 는 SpEL 을 사용한다는 것이다. SpEL(Spring Expression Language)은 런타임에 동적으로 객체 정보에 접근하고 조작할 수 있는 스프링의 표현식 언어다. 따라서 `key="ALL"` 이라고 쓰면 ALL이라는 프로퍼티를 찾으려다 실패한다. 문자열 리터럴을 넘기려면 작은 따옴표로 한 겹 더 감싸야한다.

```java
key = "'ALL'"     // SpEL 문자열 리터럴 → "ALL"   ✓
key = "ALL"       // SpEL 식 → ALL 프로퍼티 조회 → 실패
```

항목이 하나뿐인 캐시라면 `allEntries` 를 쓸 이유가 없다. 반대로 `user::1`, `user::2` 처럼 키가 여러개이고 전부 함께 무효화해야하는 구조라면 `allEntries`가 맞는 선택이다.

### 1.4 TTL은 정합성 장치가 아니다

Cache Evict를 정비하면서 TTL의 역할도 다시 정리하게 됐다. TTL이 있으니 시간이 지나면 어차피 캐시가 사라지고, 그러면 무효화를 조금 놓쳐도 자가 회복 되는 것 아닌가 하는 생각이 들 수 있다.

데이터가 이원화 됐을 때 백엔드 개발자로서 가장 주의해야할 것은 데이터 정합성이다. 이 정합성을 담당하는 것이 evict이다. TTL은 evict가 실패하거나 누락됐을 때 틀린 데이터가 최대 얼마나 오래 남는지에 대한 상한점을 설정해 두는 것이다.

```text
evict  : 데이터가 바뀌는 순간 즉시 지운다          → 정합성 담당
TTL    : 그 evict가 닿지 않았을 때
         틀린 값이 남아 있는 시간의 최대치를 제한   → 손실 상한
```

## 2. 정리

Cache Evict의 책임은 어디에 있는가에 대해 고민했던 경험을 적어보았다.

“개발자의 의도를 드러낼 수 있는가?”보다 “누구의 책임인가?”를 고려하며 설계하면 조금더 OOP적인 설계를 할 수 있다는 것을 다시 한번 체감하게 되었다. 기억에 의존하는 정책보다 설계가 강제할 수 있는 정책이 더 견고하다.

객체가 어떤 역할을 갖는지부터 정의하라는 말을 수없이 들었지만, 이렇게 설계 판단으로 이어진 경험은 처음이었다.

다음 글에서는 도입부에 적어둔 두 번째 문제, 캐시가 비워지고 갱신되는 순간 요청이 몰리는 cache stampede를 다룬다. 이 문제는 캐시만의 문제가 아니라 동시성 제어의 한 갈래이므로 락과 동시성 개념부터 정리하며 접근할 예정이다.
