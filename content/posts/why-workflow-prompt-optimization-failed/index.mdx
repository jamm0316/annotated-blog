저희 팀에는 두 종류의 AI 개발 도구가 있습니다.

하나는 Jira 티켓 기반 자동 워크플로우입니다. 티켓 번호만 넘기면 요구사항 정리부터 계획 수립, 구현, 테스트, 리뷰까지 한 번에 처리해주는 자동화 파이프라인이죠. 사람의 개입이 거의 없습니다.

다른 하나는 대화 기반 에이전트 세트입니다. 제가 즐겨 쓰는 도구로, 메인 세션에서 Claude와 충분히 설계 대화를 나눈 다음 단계별 전문 에이전트(계획 작성자 / 구현자 / 테스트 작성자 / 리뷰어)를 명령어로 불러서 마무리하는 방식입니다.

<Figure src="/posts/why-workflow-prompt-optimization-failed/01.png" alt="" width={1536} height={1024} />

두 도구를 다 써보니 대화 기반 에이전트 쪽 결과물이 더 좋았습니다. “그러면 이쪽의 엄격한 규칙들을 자동 워크플로우로 옮겨오면 양쪽 장점을 다 챙길 수 있겠는데?” 싶었죠.

그렇게 하루 동안 세 번 테스트해본 결과, 제가 손본 새 버전이 원래 자동 워크플로우보다 <strong>토큰은 79% 더 쓰고, 시간은 107% 더 걸리고, 코드 품질은 눈에 띄게 나빠졌습니다.</strong>

## 1. 두 가지를 기대했다

이번 작업은 단순히 “엄격한 규칙을 옮겨오자”가 아니라, 두 가지를 한 번에 해결하려는 시도였습니다.

<strong>기대 1 — 비용</strong>: 외부 통신을 로컬 호출로 바꾸면 토큰과 시간이 줄어들 거다.

기존 자동 워크플로우는 Jira와 MCP를 통해 한 티켓당 약 8\~10번의 외부 호출이 일어났습니다. 요구사항·계획·구현 결과·완료 보고를 매 단계마다 Jira 코멘트로 주고받았기 때문이죠. 이 통신을 로컬 파일 기반으로 바꾸면 외부 latency가 사라지고 토큰도 자연히 줄겠다 싶었습니다.

<strong>기대 2 — 품질</strong>: 대화 기반 에이전트의 엄격한 규칙을 자동 워크플로우로 옮기면 결과물 품질이 올라갈 거다.

대화 기반 에이전트에는 “리뷰어가 요구사항 항목마다 코드에서 명시적인 증거를 찾을 수 있게 하라” 같은 엄격한 검증 규칙이 들어 있었고, 이게 평소 결과물 품질을 확실히 올려줬습니다. 같은 규칙을 자동 워크플로우의 리뷰어한테도 넣으면 양쪽 도구의 장점을 다 챙길 수 있겠다 싶었죠.

이 두 가지를 노리고 산출물 저장 위치를 로컬로 옮기고, 역할별 에이전트를 분리하고, 리뷰어에게 엄격한 검증 규칙을 추가했습니다. 설계상으로는 Jira 호출 수 70% 절감과 품질 향상이 충분히 가능해 보였습니다.

## 2. 둘 다 빗나갔다

같은 티켓으로 두 버전을 비교한 수치입니다.

| 항목 | 원본 | 개선 시도 | 차이 |
| --- | --- | --- | --- |
| 총 토큰 | 274,396 | 492,104 | +79% |
| 누적 시간 | 12:23 | 25:36 | +107% |
| Jira 호출 | 8\~10회 | 3회 | –70% |

비용 쪽 기대가 먼저 빗나갔습니다. Jira 호출은 예상대로 70% 줄었는데, 정작 총 토큰은 오히려 79% 늘었고 시간은 두 배가 됐습니다. 외부 호출에서 아낀 만큼 다른 데서 더 크게 토해내고 있었던 거죠.

품질 쪽도 마찬가지였습니다. 진짜 문제는 수치가 아니라 코드였습니다. 같은 요구사항(PATCH API로 전환하면서 특정 필드는 수정 대상에서 제외)을 두 버전에 줬을 때 결과물이 이렇게 달랐습니다.

문제는 이거였습니다. 개선 시도 버전은 Spring이 알아서 처리해주는 검증 로직을 컨트롤러 안에서 직접 다시 짜고 있었습니다.

```java
// 원본 — 평범한 Spring 컨트롤러
@PatchMapping("/items/{id}")
public ResponseEntity<...> patchItem(
    @PathVariable Long id,
    @RequestBody @Valid PatchRequest request,
    @CurrentUserId long userId) { ... }
```

원본은 흔한 Spring 컨트롤러였습니다. 제외해야 할 필드가 DTO에 아예 없으니까, “제외” 요구사항이 타입만으로도 자연스럽게 막혔죠.

```java
// 개선 시도 — 같은 검증을 손으로 재작성
@RequestBody JsonNode rawBody
if (rawBody.has("excludedField")) throw new GlobalException(...);
request = objectMapper.treeToValue(rawBody, PatchRequest.class);
Set<ConstraintViolation<...>> violations = validator.validate(request);
if (!violations.isEmpty()) throw new ConstraintViolationException(violations);
```

같은 일을 하는데 코드는 길어졌고, `ObjectMapper`랑 `Validator`를 컨트롤러에서 직접 다루고 있습니다. Spring이 그냥 해주는 일을 굳이 손으로 다시 짠 겁니다. 품질을 올리겠다고 넣은 규칙이 거꾸로 품질을 떨어뜨린 셈이죠.

## 3. 같은 규칙이 정반대로 동작한 이유

대화 기반 에이전트에서 잘 통하던 엄격한 규칙들이, 자동 워크플로우에서는 왜 정반대로 동작했을까요?

답은 두 환경이 에이전트한테 주는 맥락의 양이 완전히 달랐다는 거였습니다.

대화 기반 에이전트는 맥락이 충분한 환경에서 동작합니다. 메인 세션에서 제가 Claude와 설계 방향을 충분히 합의한 뒤에 에이전트가 호출되니까, 에이전트는 이미 잡힌 방향을 더 단단하게 다듬기만 하면 됩니다. 이런 환경에서는 “명시적인 증거를 남겨라” 같은 규칙이 충분한 맥락 위에 얹히는 깔끔한 필터로 작동합니다.

자동 워크플로우는 반대입니다. Jira 티켓의 짧은 설명만 보고 다음 산출물로 넘어가는 구조라, 각 에이전트가 받는 맥락이 얇습니다. 이 상태에서 “명시적인 증거를 남겨라”는 압박이 들어가면, 구현자는 타입 시스템이 이미 막아주는 부분까지 일부러 코드로 풀어쓰게 됩니다. 앞에서 본 `JsonNode` 파싱 코드가 정확히 그 결과물입니다.

원래 자동 워크플로우도 사실은 맥락이 충분한 환경을 알게 모르게 유지하고 있었습니다. 요구사항을 Jira에 저장하기 전에 메인 세션이 저한테 질문을 던지면서 합의 대화를 거쳤고, 그 대화가 그대로 컨텍스트에 남아 있었거든요. 제가 손본 버전은 그 합의 대화를 로컬 파일에 저장하면서 맥락의 흐름을 끊어버렸습니다. 도구가 나쁜 게 아니라 동작하는 환경이 달라진 거였죠.

## 4. 비용도 같은 이유로 늘었다

비용 쪽 예상이 빗나간 것도 사실 같은 원인이었습니다.

자동 워크플로우는 각 에이전트가 받는 맥락이 얇기 때문에, 그 부족한 맥락을 채우려고 보조 문서들을 매 단계마다 다시 읽어야 합니다. 제가 추가한 워크플로우 설명 문서, 에이전트 역할 문서, README 같은 메타 문서들이 매번 컨텍스트로 들어갔죠. 외부 호출에서 아낀 토큰을, 내부 문서를 반복해서 읽는 데 더 많이 쓰고 있었던 겁니다.

결국 두 가지 기대가 같은 지점에서 무너졌습니다. 맥락이 얇은 환경에 맥락이 충분한 환경에서 잘 통하던 도구를 그대로 옮긴 게 원인이었습니다.

## 5. 배운 것

세 가지를 배웠습니다. 두 가설이 깨진 자리에서 자연스럽게 나온 결론입니다.

세 가지를 배웠습니다.

### 맥락의 양이 결과물을 좌우한다

품질 쪽 기대가 빗나간 데서 배운 점입니다. 같은 규칙도 맥락이 충분한 환경에서는 품질을 올리고, 맥락이 얇은 환경에서는 거꾸로 떨어뜨립니다. 에이전트랑 엣지 케이스나 구현 방향을 충분히 얘기한 뒤에 작업을 맡기면, 결과물이 신경 써야 할 부분을 정확하게 짚어냅니다. 앞뒤 없이 “이거 해줘”로 던지면 결과물이 고통스러워져요.

### 프롬프트가 안 맞으면 고치지 말고 다시 짜라

워크플로우 단위로 정교하게 짜인 프롬프트는 일부만 손대도 어디선가 원래 의도와 다르게 동작하기 시작합니다. 사용 환경이 달라졌다면 프롬프트도 처음부터 다시 짜는 게 맞습니다. 저는 하루를 써서 이걸 배웠습니다.

### 무엇을 얻고 싶은지 먼저 정한다

비용 쪽 기대가 빗나간 데서 배운 점입니다. 비용 절감만 보고 외부 호출을 줄였더니, 그 과정에서 맥락의 흐름까지 끊어버렸습니다. 무엇을 줄일지가 아니라 무엇을 지킬지부터 정했어야 했습니다. 충분한 맥락이 깔려 있다면 바로 작업을 맡겨도 되지만, 그렇지 않으면 한 방에 끝내는 작업은 의미가 없습니다.

결국 제가 만들고 싶은 건 맥락을 같이 만들어주는 메인 에이전트와, 그 위에서 동작하는 정교한 워크플로우의 조합이라는 데까지 왔습니다. 다음 시도는 그 방향으로 처음부터 다시 짜보려 합니다.
