서비스를 운영하다 보면 지나간 일을 되짚어야 할 때가 있다. 어제까지 우리 팀만 쓰던 정보가 오늘은 다른 팀에도 보인다. 언제부터 이런 정책이 적용된 거지? 이런 질문에 답할 수 있는 방법은 로그를 보는 것이다.

## 로그는 누가 읽는가?

로그를 읽는 소비자는 크게 2명이 있다. 첫째는 개발자, 둘째는 고객이다.

개발자의 주된 관심사는 '애플리케이션이 정상 동작하는가?' 이다. 따라서 로그를 읽는 이유는 시스템의 안정성을 확보하기 위함이다. 개발자는 중요도에 따라 TRACE, DEBUG, INFO, WARN, ERROR와 같이 로그의 층위를 나누어 개발하고. 장애 상황 시 DEBUG까지 켜고 로그를 분석할 수 있다.

고객이 로그를 읽는 이유는 위와 조금 다르다. 고객의 주된 관심사는 '언제, 누가 이 API를 사용하였는가?' 이다. 즉, 보안적 측면에서 점검하기 위해 로그를 찾아본다. 비정상 접근을 가려낼 수 있고, 때로는 책임소재를 따져볼 수도 있다.

오늘은 두번째인 고객이 사용하는 로그에 대해 정리한다. 이는 2가지 종류가 있다.

- 접근 로그(Access Log): HTTP 요청에 대한 기록
- 감사 로그(Audit Log): 유의미한 비즈니스 코드를 실행했을 때 기록

접근 로그는 이미 있었다. 게이트웨이의 필터 체인에서 모든 요청의 URL, 메서드, 상태 코드를 남긴다. 이번에 만든 것은 권한 설정 변경을 남기는 감사 로그다.

감사 로그는 무엇이 바뀌었는지 알아야 남길 수 있다. 그래서 도메인 의미를 아는 서비스 계층에서 기록하고, 접근 로그와 섞이지 않게 별도 컬렉션에 저장했다.

## 감사 로그에 접근 로그까지 담아야 한다면?

기획팀에서는 권한 변경 로그의 성공, 실패와 그 사유까지 한번에 확인하고 싶어했다. 감사 로그 한 건을 열었을 때 누가 어떤 IP에서 어떻게 요청을 보냈고, 결과는 어땠는지까지 보여 달라는 것이였다. 감사 로그 안에 접근 로그의 정보를 함께 담아 달라는 요구였다.

처음에는 기존의 감사 로그의 개념에 맞게 권한이 실제로 바뀐 경우에만 로그를 남길 생각이였는데, 이제 권한을 바꾸려다 실패한 시도도 남겨야 했다. 앞서 언급했 듯 감사 로그는 서비스 계층에서 기록하기 때문에 여기서 실패의 기준은 서비스 처리 중 실패로 정의했다. 따라서, 이름 중복, 존재하지 않는 요청, 서버 오류와 처럼 service layer validation check에서 실패하는 내용을 기록하기로 했다.

따라서, 다음 3가지를 정해야했다.

1. Document의 구조는 어떻게 정할 것인가?
2. 어떻게 객체지향적으로 설계할 수 있을까?
3. 성공과 실패를 어떻게 트랜잭션 할 것인가?

## 확장성을 고려한 문서 구조 만들기

이번 요구는 권한 변경이지만, 게정 변경이나 그룹 변경 이력도 같은 화면에서 보여달라는 요구가 생길 수 있다. 그때마다 컬렉션과 문서 구조를 새로 만들면 조회 API와 화면이 계속 늘어난다. 그래서 문서는 로그 유형이 늘어도 구조를 바꾸지 않고 행만 늘도록, 확장 가능하게 설계했다.

기준은 어느 필드가 로그 유형과 상관없고, 어느 필드가 유형마다 달라지는가였다.

- 요청 정보: 누가, 어디서, 결과가 어땠나. 접근 로그에서 가져온 정보이고, 로그 유형과 상관 없이 같다.
- 변경 정보: 무엇이 어떻게 바뀌었나. 권한 변경에만 해당한다.

```js
// AuditLogs
{
  // 요청 정보 - 어떤 로그 유형이든 같다
  actorUserId, actorUserName, actorUserEmail,
  clientIp, requestMethod, requestUrl,
  result: "SUCCESS" | "FAILURE",
  failure: { httpStatus, errorCode, message },   // 실패 건만
  requestData, responseData,                      // 실패 건만

  // 변경 정보 - 로그 유형마다 다르다
  changeType: "PERMISSION",
  targetType, targetId, targetName,               // 이름은 기록 시점 값
  changeItem,                                     // 관리자 권한, 사용자 권한, 공유 범위 …
  before: { scope, groupIds, userIds },           // ID만
  after:  { scope, groups: [{ id, name }], users: [{ id, name, email }] }
}
```

유형마다 달라지는 부분은 두 가지로 판별하도록 설계했다.

첫째는 로그 유형 판별자 `changeType`이다. 지금 값은 `PERMISSION` 하나 뿐이지만, 계정 변경 이력이 오면 `ACCOUNT` 같은 값을 하나 더 만들어 컬렉션과 조회 API는 그대로고, 목록은 이 값으로 분기하거나 필터링 할 수 있다. 또한 화면 탭 이름도 기획 초안인 '권한 설정 로그'에서 '변경 로그'로 넓혔다. 요구가 올 때마다 탭이 늘어나는 것을 막기 위해서다.

둘째는 `before`과 `after` 필드다. 무엇이 어떻게 바뀌었는지는 로그 유형마다 모양이 다르다. 권한은 공개 범위와 그룹, 사용자 목록이고, 계정이라면 이름이나 역할이 될 것이다. 이 두 필드를 권한 전용 클래스로 선언하면 유형이 늘어날 때마다 엔티티를 고쳐야 한다. 그래서 두 필드는 Jackson의 `JsonNode` 로 선언했다. 필드의 모양이 어떤 모양의 JSON으로 들어오든 그대로 저장하고, 그안의 모양은 변경 정보를 채우는 쪽에서 정하도록 했다.

```java
// 로그 유형과 상관없이 같다
private String changeType;   // PERMISSION, 이후 ACCOUNT …
private JsonNode before;
private JsonNode after;
```

다만 응답은 권한 로그 전용 DTO로 고정했다. 저장 모양이 그대로 프론트에 가면 서버에서 필드 하나만 바꿔도 화면이 깨지기 때문이다. 계약은 서로가 신뢰할 수 있는 값이여야한다고 생각한다. 따라서 저장은 유연하게, 응답은 고정으로 둔 것이다. 또한 DTO를 활용하면 `before`, `after` 안에 무엇이 있는지 코드 레벨에서 확인이 가능하다.

## 변경에 닫히고 확장에 열린 기록 구조 만들기

문서 구조를 범용으로 만들었다면, 로그를 남기는 객체도 같은 기준으로 설계해야 했다. 로그 유형이 늘어날 때 기존 코드는 건드리지 않고 새 코드만 추가할 수 있어야 한다. 개방-폐쇄 원칙이다. 최종 구조는 다음과 같다.

```text
실행을 감싸는 템플릿
 ├─ 작업 전   현재 권한 조회 (리소스마다 다른 콜백)
 ├─ 작업 실행
 ├─ 성공      다시 조회해 비교 → 공통 Recorder + 권한 Recorder (같은 트랜잭션)
 └─ 실패      공통 Recorder + 권한 Recorder (NOT_SUPPORTED) → 원래 예외를 그대로 던짐
```

### 로그를 채우는 책임은 정보의 성격에 따라 나눴다

앞에서 문서를 요청 정보와 변경 정보로 나눴다. 두 정보는 바뀌는 이유가 다르다. 요청 정보는 어떤 로그 유형이든 같고, 변경 정보는 로그 유형마다 다르다. 그래서 로그를 채우는 Recorder도 이 기준으로 나눴다.

따라서 계정 변경 로그가 추가되더라도 공통 Recorder는 그대로 두고, 유형별 Recorder 하나만 만들면 된다. 변경 이유가 다르면 클래스를 나눈다는 단일 책임 원칙을 지키면서, 개방-폐쇄 원칙도 함께 지킬 수 있는 구조라고 생각한다.

### 기록 지점은 실행을 감싸는 템플릿 한 곳에 두었다

다음은 로그를 어디서 남길지였다. 처음에는 권한을 저장하는 계층에서 남겼다. 권한이 실제로 저장되는 곳이니 전후를 비교하기 가장 정확하다고 봤기 때문이다.

하지만 이 방식은 저장 계층이 로그를 알아야 했다. 저장 계층은 권한 값만 알 뿐, 로그에 남길 리소스 이름이나 변경 전 상태는 모른다. 결국 서비스가 이 정보를 매번 저장 계층으로 넘겨야 했고, 권한을 엔티티 필드에 저장하는 리소스는 저장 계층을 거치지 않아 별도 경로가 필요했다. 실패 로그까지 더하면 기록 지점이 세 곳으로 흩어졌다.

그래서 작업 자체를 감싸는 템플릿 콜백 패턴으로 바꿨다. Spring의 `TransactionTemplate`처럼, 변하지 않는 흐름은 템플릿이 담당하고 리소스마다 다른 부분만 콜백으로 받는다. 템플릿은 작업 전에 권한을 조회하고, 작업을 실행한 뒤 다시 조회해 비교한다. 실패하면 실패를 기록하고 원래 예외를 그대로 던진다. 리소스마다 다른 것은 현재 권한을 조회하는 방법 하나뿐이다.

다만 성공할 때마다 권한을 한 번 더 조회한다. 권한 수정은 관리자가 화면에서 직접 하는 작업이라 빈도가 낮고, 단건 조회이기 때문에 이 비용은 감수했다. AOP도 고려했지만 사용하지 않았다. 조회 방법이 리소스마다 달라 어노테이션으로 표현하기 어렵고, 기록 흐름이 코드에서 드러나지 않기 때문이다. 감사 로그는 언제 어떻게 남는지 코드에서 바로 보여야 한다고 생각한다.

## 성공과 실패의 트랜잭션 분리하기

실패까지 기록하기로 하면서 가장 크게 고민한 것은 트랜잭션이다. 성공 로그와 실패 로그는 권한 변경 트랜잭션에 대해 서로 반대 조건을 요구한다.

성공 로그를 같은 트랜잭션에 둔 이유는 권한은 바뀌었는데 기록이 없는 상태가 감사 로그에서 가장 나쁜 상황이라고 생각했기 때문이다. 로그 저장이 실패하면 권한 변경도 취소되는 편이 낫다. 반대로 실패 로그는 권한 변경과 함께 롤백되면 남지 않으므로, 트랜잭션 전파 속성을 `NOT_SUPPORTED`로 두어 롤백 범위 밖에서 저장했다.

이 경계는 Recorder가 정하도록 했다. 템플릿은 언제 기록할지만 알고, 어떤 트랜잭션에서 저장할지는 Recorder가 안다. 따라서 기록 지점을 한 곳으로 모아도 트랜잭션 경계는 흔들리지 않는다.

다만 이 경계는 어노테이션 한 줄에 의존한다. 그 줄을 지워도 단위 테스트는 모두 통과했다. 단위 테스트로는 트랜잭션 경계를 검증할 수 없기 때문이다. 그래서 전파 속성 자체를 확인하는 테스트를 추가해, 누군가 이 줄을 지우면 테스트가 실패하도록 고정했다.

비교 시점도 트랜잭션을 기준으로 정했다. 실패 로그는 요청한 권한이 현재 권한과 다를 때만 남기는데, 현재 권한을 예외가 난 뒤에 읽으면 아직 롤백되기 전이라 방금 바뀐 값을 읽게 된다. 그래서 현재 권한은 항상 작업 전에 읽도록 했다.

## 결과와 남은 과제

결과적으로 기획에서 요구한 대로 감사 로그 한 건에서 권한 변경의 성공, 실패와 그 사유를 함께 확인할 수 있게 됐다. 또한 새 로그 유형이 추가되면 `changeType` 값과 유형별 Recorder 하나만 더하면 되고, 새 리소스는 권한을 조회하는 방법만 넘기면 된다. 권한을 저장하는 계층은 로그를 전혀 모른다.

남은 과제는 템플릿이 조회 함수를 믿고 동작한다는 점이다. 조회 함수가 매번 저장소를 읽지 않고 미리 읽어 둔 값을 돌려주면, 전후가 항상 같아져 오류 없이 로그가 남지 않는다. 지금은 서비스별 테스트로 막고 있지만, 새 리소스를 붙일 때 같은 테스트를 빠뜨리면 잡기 어려울 것 같다. 이 약속을 테스트가 아니라 구조로 강제할 수 있는 방법을 찾아봐야겠다.
