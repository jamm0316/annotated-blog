이전 글에서 cache evict의 책임을 어디에 둘 것인가를 정리했다. 서비스 계층에 있던 evict 선언을 DB 쓰기가 실제로 일어나는 dataAdapter로 옮겨 누락 가능이 구조적으로 사라졌다.

위 글의 도입부에서 언급했던 질문이 있었다.

> <strong><em>캐시가 비워지고 다시 채워지기 전에 요청이 몰린다면 모두 원본을 조회할 텐데, 이때의 낭비는 어떻게 대응할 것인가?</em></strong>

이는 동시성 제어 문제이므로 락 개념부터 정리하며 접근해야 이해하기 쉽다.

## 1. cache stampede란 무엇인가?

캐시가 사라진 직후를 생각해보자. 그 데이터를 찾던 요청들이 전부 cache miss를 맞고, 각자 원본 데이터를 조회한다. 이 현상을 cache stampede라고 한다.

stampede는 소 떼가 놀라서 한 방향으로 우르르 몰려가는 것을 뜻한다. 캐시가 비워진 순간 요청들이 한꺼번에 원본으로 몰려가는 모습이 이와 비슷하다.

</Figure>

이 때 두가지 문제가 발생한다.

### 중복읽기(duplicate read)

같은 데이터를 N번 조회하는 것이다. 1건을 제외한 나머지는 모두 낭비이고, 그 부하는 원본 DB가 받는다. 캐시를 두는 이유가 원본 부하를 줄이는 것인데, 하필 캐시가 없는 그 순간에 평소보다 큰 부하가 몰린다.

### 중복 쓰기(duplicate write)

같은 값을 N번 쓰는 것이다. 명령이 낭비 되는 것도 문제이지만, 더 주의할 점은 마지막에 쓴 값으로 덮어씌워진다는 것이다. 조회 시점과 쓰기 시점 사이에 데이터가 변경됐다면, 먼저 조회한 요청의 낡은 값이 나중에 저장된 최신 값을 덮어쓸 수 있다.

따라서 캐시는 evict를 고려하면 자연스럽게 stampede까지 방어를 해야한다.

## 2. 우리 서비스에서 stampede는 실제 문제가 된다

stampede를 무조건 막아야하는 것은 아니다. 대응책에는 모두 비용이 따르기 때문에, 우리 상황에서 실제로 위험한지부터 계산해야 했다.

나는 해당 API가 실제로 운영상 문제가 될지 판단하고자 현재 API가 감당할 수 있는 동시 로더 수가 어느 정도가 되는지 계산해 보았다.

```text
동시 로더 수 ≒ 재생성 시간(T) × 그 키의 초당 요청 수(R)
```

위 식을 간단히 설명하자면 캐시 미스가 난 순간부터 첫 요청이 값을 채워 넣기까지 T초가 걸린다. 그 T초 동안 도착하는 요청은 전부 캐시 미스가 된다. 따라서 동시에 원본을 조립하는 요청수가 `T × R`이 된다.

### 2.1 재생성 시간은 캐시 미스의 시간을 뜻한다

앞서 언급했 듯이 T는 캐시 미스 시간이다. 캐시를 붙이고나서 API 응답 시간이 101ms가 되었지만, stampede는 evict후 다시 조회할 때에는 캐시 미스에서 벌어지는 일이므로 재생성 시간(T)는 376ms이다.

### 2.2 초당 요청 수는 최대 700건으로 추정했다

정확한 R은 측정하지 못해 상한을 추정햇다. 고객사의 전체 사용자 약 3,000명 중 활동 인원을 70%로 보면 2,100명이다. 해당 API를 1/3이 같은 시간대에 사용한다고 잡으면 약 700건이다.

두 값을 식에 넣으면 동시 로더 수가 나온다.

```text
동시 로더 수 ≒ 0.376초 × 700건 ≈ 263개
```

위 가정에 의하면 캐시가 비는 순간 263개의 요청이 동시에 캐시 미스를 맞고 원본 데이터를 조회한다.

### 2.3 동시 로더 263개를 우리 서버가 버틸 수 있을까?

로더는 원본을 조회하는 동안 DB 커넥션을 하나씩 점유한다. 재생성 시간 전체를 DB 조회로 보면, 동시 로더 263개는 커넥션 263개를 동시에 점유하려고 시도한다.

현재 MongoDB 드라이버 기본값인 풀 크기 100을 사용하고 있다. 263개 중 100개만 커넥션을 얻고 나머지 163개는 대기하게 된다. 커넥션 풀은 애플리케이션 전체가 공유하므로, 캐시 하나가 비었다는 이유로 로그인이나 채팅처럼 무관한 API까지 대기하는 상황이 발생할 수 있었다.

700건은 최악의 상정한 값이다. 하지만 조직 수정이나 동기화 배치는 주로 업무시 시간, 즉 트래픽이 많은 시간에 일어나므로 대응하는 것이 좋다고 판단했다.

## 3. 중복 일기는 로더를 하나로 줄여 막는다

### 3.1 evict로 비는 캐시에는 single-flight로 대응한다

<Figure src="/posts/cache-stampede/02.png" alt="" width={436} height={150} />

랜덤 TTL과 PER은 TTL 만료를 전제로 만료 시점을 분산시키는 방식이다. 우리 캐시는 만료가 아니라 evict로 비워지므로 single-flight로 해결하기로 했다.

이는 동시에 여러 요청이 들어오면 1개의 요청이 원본데이터를 조회하는 동안 락을 걸어두고, 캐시 등록을 하고나면 나머지 요청들은 캐시에서 조회하도록 설계하는 방법이다.

우리 서비스는 여러 인스턴스로 떠 있어서, 분산락을 도입해야 했다.

### 3.2 Redis로 분산락을 건다.

모든 인스턴스가 이미 연결해 쓰고 있는 Redis에 락 키를 둔다.

`NX`는 키가 없을 때 쓰라는 조건이다.

키가 있는지 확인하는 명령과 키를 만드는 명령을 따로 보내면, 두 요청이 동시에 “없다"를 확인하고 둘 다 키를 만들어 락을 잡을 수 가 있다. 따라서 MongoDB에서 조회와 수정을 `findAndModify`로 묶고 `NX`는 확인과 생성을 한 명령으로 처리해 그 사이 다른 요청이 끼어들기 없게 하였다.

### 3.3 Redis는 싱글스레드인데 왜 락이 필요한가

<Figure src="/posts/cache-stampede/03.png" alt="" width={285} height={110} />

Redis는 락을 대신 걸어주는 것이 아니라, 락을 만들 수 있는 원자적 명령을 제공할 뿐이다.

싱글스레드가 보장하는 것은 명령 하나가 실행되는 동안 다른 명령이 끼어들지 않는다는 것이다. 우리가 보호하려는 구간은 명령 하나가 아니다. 캐시 조회, 원본 조립(376ms), 캐시 저장은 Redis 명령 두 번과 DB 조회 한 번으로 이뤄지고, 그 사이에 다른 인스턴스의 요청이 얼마든지 끼어든다.

locking 라이터는 이 구간 앞에 락 키를 SET NX로 만든다. NX는 키가 없을 때만 쓰라는 조건이다. 키가 있는지 확인하는 명령과 키를 만드는 명령을 따로 보내면 두 요청이 동시에 “없다”를 확인하고 둘 다 락을 잡을 수 있다. NX는 확인과 생성을 한 명령으로 처리하므로 먼저 보낸 요청만 통과한다.

### 3.4 캐시 라이터를 locking으로 교체했다

```text
// Before — non-locking: Redis 락 없음, 인스턴스마다 로더 1개
RedisCacheManager.builder(connectionFactory)

// After - locking: Redis 락, 전체 인스턴스에서 로더 1개
RedisCacheManager.builder(
        RedisCacheWriter.lockingRedisCacheWriter(connectionFactory))
```

- 대기하는 요청은 최대 376ms를 기다린다. DB 부하는 줄지만 응답 지연은 남는다.
- 대기하는 동안 락이 풀렸는지 확인하는 명령이 sleepTime 간격으로 Redis에 계속 나간다.
- 락 단위가 캐시 이름이다. 한 캐시 이름에 키가 여러 개라면 무관한 키끼리도 대기한다. 우리는 키가 `groupTree::ALL` 하나여서 문제가 없었다.

## 4. 중복 쓰기는 락과 TTL로 막는다

### 4.1 로더가 하나면 쓰기도 한 번이다

single-flight에서는 락을 잡은 요청만 원본을 조회하고 캐시에 쓴다. 나머지는 채워진 캐시를 읽기만 한다. 쓰기가 한 번으로 줄면서, 같은 값을 N번 쓰던 낭비와 서로 다른 시점에 조회한 값이 뒤늦게 덮어쓰던 문제가 함께 사라진다.

### 4.2 로더와 evict가 겹치는 경우도 락이 막는다

로더가 하나여도 낡은 값이 남을 수 있는 경우가 있다. 로더가 원본을 조회한 직후, 캐시에 쓰기 전에 데이터가 바뀌는 경우다.

```text
로더 : 락 획득 → DB 조회(변경 전 값) ──────────→ SET(낡은 값) → 락 해제
쓰기 :                  DB 변경 → evict(DEL)
```

evict가 로더의 SET보다 먼저 실행되면, 방금 지운 자리에 낡은 값이 다시 채워진다. evict는 효과가 없고, 다음 evict나 TTL 만료 전까지 틀린 값이 남는다.

locking 라이터에서는 evict도 락이 풀릴 때까지 기다린다. evict가 로더의 SET 뒤에 실행되므로 낡은 값은 곧바로 지워진다.

```text
로더 : 락 획득 → DB 조회(변경 전 값) → SET(낡은 값) → 락 해제
쓰기 :                  DB 변경 → evict 대기 ·········→ DEL
```

### 4.3 TTL은 락이 막지 못한 경우의 상한이다

그래도 TTL은 둔다. 이전 글에서 정리했듯 TTL은 정합성 장치가 아니라, evict가 닿지 않았을 때 틀린 값이 남는 시간의 상한이다. 락이 막지 못하는 경우가 생기더라도 피해는 TTL 안에서 끝난다.

## 5. 정리

stampede는 두 문제를 함께 만든다. 중복 읽기는 낭비의 문제이고, 중복 쓰기는 정합성의 문제다.

성격이 다르니 판단 방식도 달랐다. 중복 읽기는 막지 않아도 서비스는 동작하므로, `T × R`을 계산해 대응할지를 정했다. 중복 쓰기는 틀린 값이 남는 문제여서, 계산이 아니라 락이 막는 범위와 TTL이 상한을 정하는 범위를 나눠 확인해야 했다.

결과적으로 같은 락이 두 문제를 함께 줄였다. 하지만 같은 락이라도 무엇을 지키려고 거는지에 따라 판단 방식은 달라진다.
