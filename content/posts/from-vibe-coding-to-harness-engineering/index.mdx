최근 몇년 간 에이전틱 코딩이 대세가 되면서, 내심 이런 기대와 함께 사용했습니다.

"그냥 알아서, 잘, 딱, 깔끔하고, 센스있게 해줬으면 좋겠다."

AI는 생각보다 훨씬 잘 해줬지만, 제가 애매하게 시키면 결과도 애매하게 나왔습니다. 문제는 AI가 아니라 <strong>제 프롬프트였죠.</strong>

그 의문을 가지고 읽은 책이 [<em>바이브 코딩 너머 개발자 생존법</em> (Addy Osmani 저)](https://product.kyobobook.co.kr/detail/S000218400836)였고, 어제는 관련 세미나에 다녀왔습니다. Goos Kim(모두의AI 공장장)님이 직접 개발한 오픈소스 [MoAI-ADK](https://github.com/modu-ai/moai-adk)를 주제로 구름에서 주최한 세미나로, 책에서 읽은 개념들이 실제로 어떻게 구현되는지 볼 수 있었습니다.

## 1. 바이브 코딩과 AI 보조 엔지니어링은 다릅니다

책에서 가장 먼저 구분하는 개념이 이 둘이었습니다.

<strong>바이브 코딩(Vibe Coding)</strong> 은 그린필드, 즉 처음부터 새로 짜는 환경에서 유용합니다. 개인 토이 프로젝트, 빠른 프로토타입, 혼자 쓸 스크립트 같은 경우죠. AI에게 흐름을 맡기고 빠르게 결과를 만들어내는 방식입니다.

<strong>AI 보조 엔지니어링(AI-Assisted Engineering)</strong> 은 브라운필드에서 씁니다. 이미 팀이 있고, 레거시가 있고, 보안 요구사항이 있는 실제 프로덕션 환경이죠.

문제는 많은 사람들이 바이브 코딩 방식으로 상용 서비스를 개발하려 한다는 점입니다. 책에서는 이 부분을 명확히 지적합니다. 바이브 코딩만으로는 상용화가 어렵다고요. 특히 보안이 대표적입니다. AI는 동작하는 코드를 만들어주지만, SQL Injection이나 인증 로직, 권한 검증 같은 보안 요구사항을 맥락 없이 만족시키기는 어렵습니다. AI가 만든 코드라도 보안은 개발자가 직접 리뷰하고 책임져야 합니다.

저도 처음엔 둘을 구분하지 않고 쓰고 있었습니다. 업무 코드를 짤 때도 토이 프로젝트 짜듯 프롬프트를 던지고, 결과가 이상하면 다시 던지고. 책을 읽고 나서야 "아, 내가 틀린 방식으로 접근하고 있었구나" 싶었습니다.

그렇다면 프로덕션 환경에서 AI를 제대로 쓰려면 무엇부터 바꿔야 할까요? 결국 프롬프트에서 시작됩니다.

---

## 2. 프롬프트 품질이 곧 결과의 품질입니다

책에서 가장 와닿은 문장이 있었습니다.

> <em>"옆 사람에게 일을 시킨다고 생각하고 프롬프트를 써라."</em>

내가 쓴 프롬프트를 동료 개발자가 읽었을 때, 그 사람이 그대로 따라해서 일을 완성할 수 있을 정도여야 한다는 뜻이었습니다.

Claude 프롬프트 가이드에서도 같은 이야기를 합니다. <strong>성공 기준이 명확하지 않으면 먼저 이를 수립하는 데 시간을 투자하라</strong>고 권고하고 있죠.

  <a href="https://platform.claude.com/docs/ko/build-with-claude/prompt-engineering/overview">Claude 프롬프트 엔지니어링 가이드 — 성공 기준의 명확한 정의를 전제 조건으로 제시</a>

저는 이걸 읽고 나서 프롬프트를 다시 보게 됐습니다. <br />"인증 관련 API 만들어줘" 같은 프롬프트가 얼마나 무책임한 시도였는지요. 구체적인 제약 조건, 예외 케이스, 기대 출력 형태 — 이 모든 걸 명시해야 원하는 결과가 나옵니다.

CoT(Chain of Thought) 방식도 유용했습니다. AI가 단계적으로 사고하도록 유도하는 프롬프트 기법인데, 복잡한 구현을 시킬 때 "먼저 요구사항을 정리하고, 그 다음 설계를 제안하고, 마지막으로 구현해" 같은 식으로 흐름을 잡아주면 결과 품질이 달라지더군요.

다만 프롬프트를 잘 쓰는 것만으로는 한계가 있었습니다. 복잡한 기능을 구현하려면 매번 긴 프롬프트를 처음부터 작성해야 했으니까요. 세미나에서 배운 하네스 엔지니어링은 이 문제에 대한 구조적인 답이었습니다.

---

## 3. 하네스 엔지니어링 — AI에게 코드가 아니라 환경을 준다

어제 세미나에서 가장 새로 배운 개념이 <strong>하네스 엔지니어링(Harness Engineering)</strong> 이었습니다.

<Figure src="/posts/from-vibe-coding-to-harness-engineering/05.png" alt="" width={1375} height={768} />

Goos님은 이 개념을 직접 구현한 오픈소스 툴을 만든 분이었습니다. [MoAI-ADK](https://github.com/modu-ai/moai-adk) — Claude Code를 위한 Agentic Development Kit입니다. 추상적인 이야기가 아니라 실제로 동작하는 워크플로우를 보여주셨기 때문에 훨씬 와닿았습니다.

> <em>"코드를 직접 작성하는 대신, AI 에이전트를 위한 환경을 설계한다."</em>

저는 이것이 하네스 엔지니어링의 핵심이라 느꼈습니다.

그 환경의 중심에 <strong>Project 문서와 Plan 문서</strong>가 있습니다. Project 문서에는 프로젝트 개요, 타깃, 핵심기능 등 '무슨 프로젝트인가'가 담깁니다. Plan 문서에는 EARS 포맷을 활용한 기능 요구사항, 구현 계획, 인수 조건 등 '어떻게 만들 것인가'가 담기죠.

AI 에이전트는 이 문서들을 읽고 작업합니다. 문서가 곧 AI에게 주는 컨텍스트입니다.

MoAI-ADK에서 실제 워크플로우는 이런 흐름입니다.

<Figure src="/posts/from-vibe-coding-to-harness-engineering/06.png" alt="" width={724} height={436} />

```bash
/moai project   # product.md, structure.md, tech.md 생성
/moai plan "사용자 인증 기능 추가"   # SPEC 문서 생성
/moai run SPEC-AUTH-001              # 구현
/moai sync SPEC-AUTH-001             # 문서 동기화 & PR 생성
```

project → plan → run → sync. 각 단계에서 문서가 갱신되고, 그 문서가 다음 단계의 컨텍스트가 됩니다.

이 구조가 곧 "<strong>통제와 자율의 균형</strong>"이었습니다. Spec 문서로 방향과 제약 조건을 잡아주는 것이 <strong>통제</strong>이고, 그 안에서 AI가 구현 방법을 스스로 판단하며 실행하는 것이 <strong>자율</strong>입니다. 좋은 문서 없이 AI에게 복잡한 작업을 시키면, 상황 설명 없이 일을 맡기는 것과 같습니다. 자율만 있고 통제가 없는 상태죠. 결과가 좋을 리 없습니다.

Goos님는 이걸 한 문장으로 정리했습니다.

> <em>"에이전틱 코딩은 속도가 아니라 품질이 중요하다. (속도는 기본)"</em>

이 말을 듣고 엔지니어의 역할이 코드 작성에서 하네스 설계로 전환 되는 것이 아닐까 하는 생각이 들었습니다. Spec을 쓰고, 품질 게이트를 정의하고, 피드백 루프를 구성하는 것. 이런 것들이 AI 시대에 개발자의 핵심 역량이 되겠구나 싶었습니다.

## 4. 주니어 개발자로서 느낀 것

Goos님의 발표를 듣고 실제로 워킹하는 MoAI를 보면서, 에이전틱 코딩으로 사람이 직접 만들어내는 수준의 품질을 유지할 수 있겠다는 기대가 좀 더 구체화됐습니다.

AI는 분명 좋은 도구이지만, 품질을 유지하려면 결국 판단 기준이 있어야 합니다. 어떤 코드가 좋고 나쁜지, 어떤 설계가 맞는지.<br />그 기준이 있어야 AI 출력을 제대로 검토할 수 있으니까요.

주니어인 저는 그 기준을 지금 만들어가는 중입니다. 그래서 실제로 MoAI를 사용해보고, 이번 세미나를 통해 배운 Spec 문서로 통제하고, 품질 게이트로 검증하는 흐름을 실제 업무에 적용해 보고자 합니다.

## 마치며

이번 세미나를 통해 세 가지를 배웠습니다.

<strong>바이브 코딩은 그린필드에서.</strong> <br />프로덕션 코드는 AI 보조 엔지니어링으로 접근해야 합니다. 둘은 다릅니다.

<strong>프롬프트는 동료에게 주는 지시서.</strong> <br />하지만 매번 프롬프트를 처음부터 쓰는 대신, Project 문서와 Plan 문서로 환경을 만들어두는 것이 하네스 엔지니어링의 핵심입니다.

<strong>AI가 만든 코드도 내 코드.</strong> <br />특히 보안은 사람이 직접 책임져야 합니다. AI에게 자율을 주되, 통제를 잃지 않는 것. 그 균형을 잡는 게 이 시대 개발자의 역할이라고 느꼈습니다.
