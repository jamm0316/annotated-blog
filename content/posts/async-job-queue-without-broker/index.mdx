사내 OCR 판독 에이전트와 RAG 시스템을 이용하여 영수증 이미지나 계약 관련 문서를 보내면 AI가 판독한 값을 돌려주는 연동을 맡았다. 판독 한 건은 OCR 기준 최대 10분, 계약 관련 문서는 최대 30분 정도가 걸렸다.

HTTP 요청을 열어 둔 채 수십 분을 기다릴 수 없다. 요청을 받으면 바로 접수 응답을 주고, 판독은 뒤에서 처리한 뒤 결과를 따로 보내야 했다. 이렇게 비동기로 처리할 일이 생기면 보통 Kafka나 RabbitMQ 같은 메시지 큐를 먼저 떠올린다. 하지만 우리 서비스에는 메시지 브로커가 없었다.

그렇다면 이미 쓰고 있는 Redis에 작업을 넣고, 리스너가 꺼내 처리하면 되지 않을까?

이 질문에 답하려면 큐가 무엇을 해 줘야 하는지부터 정해야 했다. 큐에 필요한 연산은 세 가지다.

- 작업을 넣는다
- 작업 하나를 꺼낸다.
- 꺼낸 작업은 다른 소비자가 가져가지 못한다.

이 세 연산만 보면 저장소가 무엇이든 큐로 쓸 수 있다고 생각했다. 따라서 비동기 연산을 MongoDB 문서로 구현했고, 이후 ZIP 다운로드 같은 API를 구현할 때에도 같은 구조를 썼다. 이 글은 그 설계 과정과 트레이드오프를 정리한 기록이다.

## 브로커 없이 MongoDB를 큐로 고른 이유

후보는 다섯 가지였다. 작업이 사라지지 않는지, 파드가 여러 개여도 동작하는지, 새로 운영할 인프라가 생기는지를 기준으로 비교했다.

| 후보 | 장점 | 우리 상황에서의 문제 |
| --- | --- | --- |
| Kafka | 유실 없음, 대용량 처리 | 브로커를 새로 구축·운영해야 한다. 하루 수십~수백 건 규모에 맞지 않는다 |
| Redis 큐 | 이미 있는 인프라 | 단일 인스턴스를 다른 서비스와 함께 쓰고 있어 장애가 번질 수 있다 |
| 인메모리 큐 | 가장 가볍고 바로 시작한다 | 재시작이나 배포 때 대기 중인 작업이 사라진다 |
| Change Streams | 폴링 없이 변경을 받는다 | resume token 보관과 재연결 처리가 붙어 폴링보다 복잡하다 |
| MongoDB 폴링 | 추가 인프라 없음, 유실 없음 | 폴링 주기만큼 처리 시작이 늦다 |

MongoDB를 고른 이유는 새로 운영할 인프라를 만들지 않고, 작업 상태를 한 곳에서만 관리하기 위해서다. 요청마다 진행 상태, 실패 사유, 재시도 횟수를 남겨야 했으므로 요청 1건당 MongoDB 문서 1개는 어떤 큐를 쓰든 필요했다. 여기에 Redis 같은 큐를 더하면 같은 작업 상태가 두 곳에 생기고, MongoDB 저장과 큐 넣기는 하나의 트랜잭션으로 묶을 수 없다. MongoDB 저장은 성공하고 큐 넣기가 실패하면 그 작업은 영원히 처리되지 않는다. 그래서 이력 문서를 이원화하지 않기로 결정했다.

이 선택이 가능했던 것은 [MongoDB가 단일 문서 갱신의 원자성을 보장하기 때문이다](/posts/mongodb-writeconflict-112). 조회와 상태 변경을 한 번의 연산(findAndModify)으로 처리하면 여러 파드가 같은 작업을 동시에 노려도 한 파드만 가져간다. 따라서 꺼낸 작업을 다른 소비자가 가져가지 못하게 하는 일을 분산 락이나 Redis 없이 DB만으로 보장할 수 있었다. 이 특성이 MongoDB에만 있는 것은 아니다. RDB도 행 단위 조건부 UPDATE나 SELECT … FOR UPDATE SKIP LOCKED로 같은 구조를 만들 수 있다. 결국 따져야 했던 것은 이미 상태를 저장하고 있는 곳이 원자적인 조건부 갱신을 지원하는지였다고 생각한다.

폴링 지연은 받아들였다. 폴링 주기는 5초였고, 판독 자체가 분 단위라 몇 초 늦게 시작하는 것은 문제가 되지 않는다고 판단했다. 문서를 먼저 저장하고 폴러가 그 문서를 읽어 처리하는 구조라, 결과적으로 트랜잭셔널 아웃박스 패턴과 같은 모양이 된다.

## 고려사항

요구사항은 아래와 같았다.

- 재시작이나 배포 중에도 접수한 작업을 잃지 않는다
- 파드가 여러 개여도 한 작업은 한 번만 처리한다
- 작업마다 진행 상태와 실패 사유를 조회할 수 있다

아래 두 경우를 실패로 봤다.

- 접수 응답은 성공했는데 결과가 전달되지 않는다
- 같은 작업을 두 번 처리해 AI 호출 비용이 두 번 나간다

분산 환경에서 같은 작업을 여러 개의 워커가 동시에 가져가는 문제는 원자적 선점으로 풀렸다. 따라서 결과가 끝내 전달되지 않거나 같은 작업이 두 번 처리되는 경우를 어떻게 막을지 고민하였고, 아래 3가지를 설계 핵심 포인트로 봤다.

1. 큐를 쌓아 두는 '접수'와 실제 에이전트를 호출하는 '판독'을 구조적으로 어떻게 분리할까?
2. 처리 도중 워커가 죽거나 응답이 늦으면 작업을 어떻게 되찾을까?
3. 판독이나 콜백이 실패하면 어디부터 다시 시도할까?

## MongoDB 작업 큐 아키텍처

### 문서 하나가 작업 하나인 구조

작업 하나는 MongoDB 문서 하나다. 작업을 넣고 꺼내는 일 모두 문서의 상태 필드로 처리한다. 접수 API가 RECEIVED 문서를 저장하면 작업이 들어간 것이고, 폴러가 RECEIVED 문서를 PROCESSING으로 바꾸며 가져가는 것이 작업을 꺼낸 것이다. PROCESSING이 된 문서는 다른 폴러의 조회 조건에 걸리지 않으므로 다른 워커가 가져갈 수 없다.

<QueueMapPlayground caption="작업 큐 구성 요소. 누르면 그 요소가 부르는 대상과 쓰는 저장소 메서드가 보인다" />

구성 요소는 접수 API와 스케줄러 네 개다. 모든 구성 요소는 서로를 직접 부르지 않고 작업 문서의 상태만 보고 움직인다. 폴러가 주기적으로 작업을 가져오고(Polling Consumer), 여러 파드의 폴러가 같은 작업을 두고 경쟁하되 하나만 가져가는(Competing Consumers) 구조다.

| 구성 요소 | 주기 | 하는 일 |
| --- | --- | --- |
| 접수 API | 요청마다 | 이미지를 저장하고 `RECEIVED` 문서를 만든 뒤 바로 응답한다 |
| 판독 폴러 | 5초 | 빈 자리만큼 `RECEIVED` 작업을 선점해 워커 스레드풀에 넘긴다 |
| 통지 폴러 | 5초 | 판독이 끝난 작업의 결과를 요청 시스템에 보낸다 |
| 멈춘 작업 회수 | 60초 | 오래 멈춘 `PROCESSING` 작업을 `RECEIVED` 로 되돌린다 |
| 파일 정리 | 하루 1회 | 보관 기간이 지난 이미지 파일을 지운다 |

요청 시스템이 판독을 요청하면 접수 API는 파일을 저장하고 RECEIVED 문서를 만든 뒤 바로 접수 응답을 준다. 요청 시스템은 이 응답을 받고 판독을 기다리지 않는다. 이후 판독 폴러가 5초마다 RECEIVED 문서를 찾아 PROCESSING으로 바꾸며 가져가고, 워커 스레드가 AI 에이전트에 판독을 요청한다. 판독 결과를 받으면 워커는 결과를 문서에 저장하고 상태를 DONE으로 바꾼다. 마지막으로 콜백 폴러가 DONE 문서를 가져가 요청 시스템에 결과를 보내고, 전송을 마치면 NOTIFIED로 닫는다.

그림에서 각 단계는 앞 단계를 직접 부르지 않는다. 접수 API는 판독 폴러를 모르고, 판독 워커는 콜백 폴러를 모른다. 모두 MongoDB 문서의 상태가 바뀐 것만 보고 다음 일을 시작한다. 그래서 어느 한 단계가 멈춰도 그 앞까지 처리된 작업은 문서에 남아 있다.

## 접수는 문서 저장까지, 판독은 워커 스레드에서

접수 API는 이미지나 PDF 등을 저장하고 RECEIVED 문서를 만든다. 판독은 폴러가 이 문서를 가져가 워커 스레드에서 처리한다. 접수와 처리 사이에 메모리 대기열이 없으므로 워커가 모두 작업을 실행 중이어도 접수된 작업은 RECEIVED로 남아 있다가, 작업을 끝낸 워커가 생기면 폴러가 다음 주기에 가져간다.

폴러는 앞에서 말한 findAndModify 한 번으로 작업을 선점한다.

```js
db.jobs.findOneAndUpdate(
  { status: "RECEIVED",
    $or: [{ nextAttemptAt: null }, { nextAttemptAt: { $lte: now } }] },
  { $set: { status: "PROCESSING", processingStartedAt: now } },
  { sort: { receivedAt: 1 }, returnDocument: "after" }
)
```

두 폴러가 같은 문서를 노리면 MongoDB에 의해 findAndModify가 원자적으로 처리되어 한쪽만 PROCESSING으로 바뀐 문서를 받고, 다른 쪽은 조건에 맞는 다음 문서를 받거나 null을 받는다. 원자성이 문서 단위라 A 파드가 1번 작업을 가져가는 동안 B 파드는 2번 작업을 가져갈 수 있다. 따라서 파드를 늘리면 처리량도 함께 늘어난다.

같은 이유로 폴러에 분산 락(ShedLock)을 걸지 않았다. 분산 락을 걸면 여러 파드 중 하나만 폴러를 실행하므로 겹침은 막지만 파드를 늘려도 처리량이 그대로다. 다만 선점할 단위가 없는 파일 정리 스케줄러에는 분산 락을 걸었다. 파드마다 같은 파일 목록을 지우는 것은 낭비라 판단했다.

선점한 작업은 폴러가 직접 처리하지 않고 전용 스레드풀에 넘기도록 했다. 스프링 스케줄러 스레드는 기본 1개이고, 기존 배치 작업들이 이 스레드를 함께 쓰고 있었다. 폴러가 판독 응답을 기다리면 그동안 기존 배치가 예외나 로그 없이 밀릴 수 있었기 때문이다.

## 멈춘 작업은 회수하기

워커가 판독 도중 죽으면 문서는 PROCESSING으로 남는다. 이렇게 되면 어떤 폴러도 그 작업을 다시 가져가지 않아 고아 상태로 남아 있을 수 있다. 따라서 회수 스케줄러를 두어 60초마다 처리 시작 시각을 조회해, 현재 시각으로부터 20분이 지났는데도 여전히 PROCESSING으로 남아 있는 작업을 RECEIVED로 되돌리고 재시도 횟수를 올리도록 설계했다.

회수 기준은 OCR 판독 에이전트의 과거 처리 시간을 토대로 정했다. 가장 오래 걸린 판독이 10분 정도였으므로 여유를 두어 타임아웃을 15분으로 정했다. 따라서 회수 기준은 이 타임아웃보다 길게 20분으로 뒀다. 정상 워커는 15분 안에 응답을 받거나 타임아웃으로 끝난다. 회수 기준이 타임아웃보다 짧으면 아직 응답을 기다리는 멀쩡한 작업을 회수하고, 다른 워커가 같은 작업으로 AI를 한 번 더 호출할 수 있다.

## 실패한 단계부터 다시 시도하기

실패는 두 군데서 난다. AI 판독이 실패할 수도 있고, 판독 결과를 요청 시스템에 보내는 콜백이 실패할 수도 있다.

<FailurePointPlayground caption="판독 실패와 콜백 실패 지점. 실패 지점과 재시도 방식을 바꿔 다시 실행되는 줄을 본다" />

판독 실패는 토큰이 차감되기 전이고, 콜백 실패는 판독이 끝나 토큰이 차감된 뒤다. 두 실패를 같은 재시도로 묶으면 콜백만 실패해도 판독을 다시 하게 되고, 토큰이 중복으로 차감된다. 그래서 판독과 콜백은 다른 폴러, 다른 스레드풀, 다른 재시도 횟수를 쓰도록 했다. 콜백 폴러는 판독이 끝난 작업만 가져가므로 콜백 실패가 판독 재호출로 번지지 않는다.

재시도는 다시 해서 결과가 달라질 수 있는 실패에만 한다.

- 연결 실패, 5xx: 1분, 10분, 60분 간격으로 최대 3번 다시 시도한다
- 요청 형식 오류처럼 다시 해도 같은 실패: 바로 실패로 끝낸다
- 판독 타임아웃: 다시 시도하지 않는다. AI가 이미 끝낸 판독을 다시 요청하면 토큰이 다시 차감될 수 있기 때문이다

재시도 간격을 1분, 10분, 60분으로 점점 늘린 것은 금방 끝나는 장애와 오래 걸리는 장애를 한 정책으로 묶기 위해서다. 상대 시스템이 재시작 중이라면 1분 뒤 재시도로 충분하고, 배포처럼 오래 걸리는 장애는 10분, 60분 뒤 재시도가 받아낸다.

재시도는 작업 문서에 다음 시도 시각(nextAttemptAt)을 적어 예약한다. 앞에서 본 선점 쿼리는 이 시각이 지난 작업만 가져가므로, 재시도를 기다리는 작업도 메모리 대기열이 아니라 MongoDB 문서에 남는다. 따라서 재시도를 기다리는 동안 파드가 재시작돼도 예약은 사라지지 않는다.

다만 콜백은 같은 결과가 두 번 전달될 수 있다. 결과를 보낸 직후, 보냈다는 기록을 남기기 전에 파드가 죽으면 콜백 폴러는 그 작업을 아직 보내지 않은 것으로 보고 다시 보내기 때문이다. 이렇게 적어도 한 번은 전달하되 중복될 수 있는 방식을 최소 한 번(at-least-once) 전달이라고 한다. 따라서 받는 쪽은 같은 결과를 두 번 받아도 한 번 받은 것과 같게 처리해야 한다. 이 문제는 Redis 큐를 썼어도 그대로 남는다. 분산 환경에서 정확히 한 번 전달은 큐 선택으로 해결되지 않는다고 생각한다.

## 업무에 맞춰 추가로 고려한 것

같은 구조를 다른 업무에 옮기면서 업무마다 다른 조건이 생겼다. 선점, 회수, 재시도는 그대로 두고 상태와 저장 구조만 바꿨다.

## 처리할 파일이 아직 없다면?

계약 관련 문서는 접수 시점에 검토할 문서가 준비되지 않았다. 원본 파일을 검토 가능한 형식으로 변환하는 작업이 끝나야 AI에 보낼 수 있었다. 이 상태로 RECEIVED에 두면 워커가 변환이 끝나지 않은 작업을 가져가 판독에 실패할 수 있기 때문에, 작업 상태 앞에 대기 단계를 하나 더 두었다.

접수된 작업은 WAITING 상태로 시작하고, 워커는 READY 상태의 작업만 가져간다. 그 사이는 승격 스케줄러가 잇는다. 승격 스케줄러는 30초마다 변환이 끝났는지 확인하고, 끝난 작업을 READY로 바꾼다. 변환 확인은 5분, 15분, 40분 간격으로 세 번까지 하고, 그래도 끝나지 않으면 실패로 닫는다. 승격 단계는 상태를 바꾸지 않고 선점 시각만 기록해 선점했다. 이 시각이 5분보다 오래되면 다른 승격 스케줄러가 다시 가져갈 수 있으므로, 승격 도중 파드가 죽어도 따로 회수 스케줄러를 둘 필요가 없다.

변환 실패는 별도 상태를 만들지 않고 AI 처리 실패와 같은 상태로 두되, 어느 단계에서 실패했는지만 필드로 따로 적었다. 실패 상태가 하나이므로 콜백 폴러는 쿼리 하나로 모든 실패를 요청 시스템에 알린다.

큐 코드는 공통 모듈로 묶지 않고 이 연동 안에 새로 만들었다. 그래서 영수증 판독 쪽 코드는 건드리지 않고 대기 단계와 상태를 더할 수 있었다.

## 작업 하나가 문서 수만 건을 묶는다면?

문서 변환 결과를 ZIP으로 내려받는 기능은 작업 하나가 문서 수만 건을 묶는다. 받은 ZIP을 다시 올릴 때 업로드 한도에 걸리지 않도록 파일 하나는 500MB 또는 1만 건을 넘지 않게 나눠야 했고, 진행 상황을 화면에 보여 줘야 했다.

문제는 분할마다 담을 문서 ID 목록을 작업 문서 하나에 모두 넣으면 MongoDB 문서 크기 한도인 16MB를 넘을 수 있다는 점이었다. 그래서 작업 문서 하나와 분할 문서 여러 개를 다른 컬렉션에 두도록 했다. 작업 문서는 영수증 판독처럼 폴러가 선점하고, 분할 문서는 분할마다 상태와 처리 건수를 가진다. 분할 하나가 실패해도 다음 분할을 계속 만들고, 사용자는 실패한 분할만 다시 요청할 수 있다.

이 작업은 정상이어도 수십 분이 걸린다. 처리 시작 시각만 보면 멈춘 작업과 오래 걸리는 작업을 구분할 수 없어, 멀쩡히 진행 중인 작업을 회수할 수 있었다. 그래서 회수 기준을 처리 시작 시각에서 마지막 진행 시각으로 바꿨다. 워커는 100건을 처리할 때마다 진행 시각을 기록하고, 회수 스케줄러는 이 시각이 30분 넘게 갱신되지 않은 작업만 회수한다.

## 큐를 고르기 전에 정할 것

영수증 판독, 계약 문서 판독, ZIP 다운로드에 같은 구조를 쓰는 동안 상태 전이, 선점, 재시도 구조는 거의 바뀌지 않았다. 특히 계약 문서 연동은 진행 중에 외부 시스템과의 규약이 여러 번 바뀌었다. 콜백 본문 형식이 바뀌었고, 성공 여부를 HTTP 상태 코드 대신 응답 본문으로 판단하게 됐고, 변환 대기 상한도 바뀌었다. 그때마다 고친 곳은 접수 검증, 응답 해석, 본문 조립 같은 바깥 경계였다. 어떤 작업을 누가 언제 처리하는지는 큐가, 무엇을 보내고 어떻게 해석하는지는 업무 코드가 맡도록 나눠 둔 덕분이라고 생각한다.

비동기 처리가 필요하다고 해서 바로 메시지 큐를 고를 필요는 없다고 생각한다. 이미 작업 상태를 저장하는 곳이 있다면 그곳이 큐가 될 수 있다. 다만 어떤 큐를 쓰든 멈춘 작업 회수, 회수 뒤 이중 실행, 중복 전달 문제는 남는다. 큐를 고르기 전에 이 세 가지를 어떻게 다룰지 먼저 정하는 편이 낫다고 본다.

남은 과제는 아래와 같다.

- 회수에 상한이 없다. 회수는 재시도 횟수를 올리기만 하고 상한을 확인하지 않는다. 처리할 때마다 파드를 죽게 만드는 작업이 있다면 회수와 재처리가 끝없이 반복될 수 있다.
- 회수와 호출 실패가 같은 재시도 횟수를 쓴다. 그래서 한 번 회수된 작업은 재시도 기회를 일찍 소진한다.
- 영수증 판독 콜백은 아직 HTTP 상태 코드로 성공 여부를 판단한다. 두 연동이 같은 게이트웨이를 지나는데도 큐 코드를 공통 모듈로 묶지 않고 복제했기 때문에, 계약 문서 연동에서 고친 판단 방식이 이쪽으로 이어지지 않았다.

폴링 부하가 실제로 문제가 되는 규모는 운영 지표를 쌓아 봐야 알 수 있을 것 같다. 그 규모에 닿으면 MongoDB를 기준 저장소로 두고 Redis는 워커를 깨우는 신호로만 쓰는 방식을 검토해 볼 생각이다. 신호가 유실돼도 폴링이 안전망이 된다.
