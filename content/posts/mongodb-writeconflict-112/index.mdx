고객사 운영 환경의 알람에서 MongoDB WriteConflict(error 112)가 리포트됐습니다. 발생 지점은 매일 새벽 1시에 도는 만료 파일 삭제 배치였습니다.

결론부터 적으면, 해결은 메서드에서 `@Transactional` 한 줄을 지운 것이었습니다. 다만 그 한 줄을 지우기까지 112가 무엇을 뜻하는지부터 따라가야 했습니다.

## 1. 증상

발생 지점은 만료 파일 삭제 스케줄러였습니다. `@Scheduled(cron = "0 0 1 * * *")`로 매일 01:00에 도는 배치입니다. 이 배치가 112 예외로 중단되면, 그 회차에 수거해야 할 만료 파일 일부가 그날 삭제되지 않습니다.

다만 이 배치는 멱등해서, 다음 날 01:00에 같은 만료 파일을 다시 수거합니다. 삭제가 하루 지연되는 수준이었죠. 이 멱등성은 뒤에서 해결 방향을 정하는 근거가 되니 기억해 두겠습니다.

ERROR 알람은 충돌 지점과 충돌 상대까지 적어줬지만, 일단 writeConflict(112)가 정확히 무엇인지부터 확인하기로 했습니다.

---

## 2. WiredTiger는 충돌을 어떻게 다루는가

MongoDB의 기본 스토리지 엔진인 <strong>WiredTiger는 대부분의 읽기/쓰기에 낙관적 동시성 제어(OCC, Optimistic Concurrency Control)를 사용</strong>합니다. 비관적 락처럼 문서를 미리 잠그는 대신, 일단 동시 작업을 허용하고 충돌이 감지되면 한쪽을 되돌리는 방식입니다.

이를 받쳐주는 것이 MVCC(Multi-Version Concurrency Control)입니다. 공식 문서의 설명은 간결합니다. 연산이 시작될 때, WiredTiger는 그 연산에 데이터의 특정 시점 스냅샷(point-in-time snapshot)을 제공합니다. 연산은 이 스냅샷을 기준으로 작업하죠.

<Figure src="/posts/mongodb-writeconflict-112/01.png" alt="[MonogDB Docs] 스냅샷 및 체크포인트" width={2522} height={1738}>
  [MonogDB Docs] 스냅샷 및 체크포인트
</Figure>

<strong>충돌은 이 스냅샷이 어긋나는 순간 정의됩니다.</strong> 스레드 A와 스레드 B가 같은 문서를 동시에 수정한다고 해보죠. A가 작업하는 사이 B가 그 문서의 버전을 바꿔놓으면, A가 들고 있던 스냅샷과 실제 문서의 버전이 달라집니다. 엔진은 이 어긋남을 write conflict로 감지합니다.

<Figure src="/posts/mongodb-writeconflict-112/02.png" alt="[그림] 두 스레드가 같은 v1 스냅샷으로 시작했다가, 한쪽이 먼저 커밋해 원본이 v2로 바뀌면, 여전히 v1을 기준으로 쓰려는 다른 쪽이 버전 불일치로 write conflict를 일으킨다." width={1672} height={941}>
  [그림] 두 스레드가 같은 v1 스냅샷으로 시작했다가, 한쪽이 먼저 커밋해 원본이 v2로 바뀌면, 여전히 v1을 기준으로 쓰려는 다른 쪽이 버전 불일치로 write conflict를 일으킨다.
</Figure>

이렇게 충돌이 감지되면 한쪽 작업에 write conflict가 발생하고, <strong>MongoDB는 그 작업을 재시도합니다. 충돌을 에러로 던지는 게 아니라, WiredTiger가 알아서 다시 시도해 사용자에게 보이지 않게 흡수하는 것이 기본 동작</strong>입니다.

<Figure src="/posts/mongodb-writeconflict-112/03.png" alt="[MonogDB Docs] 문서 수준 동시성" width={2506} height={696}>
  [MonogDB Docs] 문서 수준 동시성
</Figure>

여기서 한 가지 의문이 생깁니다. 서버가 알아서 재시도해 준다면, 우리 애플리케이션은 왜 112를 보게 된 걸까요?

## 3. 트랜잭션 안과 밖은 다르게 동작한다.

<strong>충돌 처리 방식은 쓰기가 트랜잭션 안에 있느냐 밖에 있느냐에 따라 완전히 달라집니다.</strong>

2장에서 본 “투명한 재시도”는 트랜잭션 밖의 단일 쓰기에 해당하는 이야기입니다.(여기서 트랜잭션은 비즈니스 로직에서 하나로 묶어놓은 동작단위를 의미합니다.) 트랜잭션 없이 날아간 단일 쓰기는 충돌이 나도 MongoDB가 내부에서 알아서 재시도하므로, 클라이언트는 112를 보지 못합니다.

멀티-도큐먼트 트랜잭션 안에서는 이야기가 달라집니다. 공식 <strong>Retryable Writes 문서는 트랜잭션 내부의 쓰기 연산이 개별적으로 재시도되지 않는다고 명시합니다.</strong> <strong>트랜잭션 안에서 충돌이 나면 mongod는 내부 재시도를 포기하고, 트랜잭션을 abort시킨 뒤 </strong>`TransientTransactionError`<strong> 라벨이 붙은 112를 애플리케이션으로 던집니다.</strong> 이때부터는 애플리케이션이 트랜잭션 전체를 다시 실행할 책임을 집니다.

<Figure src="/posts/mongodb-writeconflict-112/04.png" alt="[그림] 같은 충돌이라도 트랜잭션 밖에서는 서버가 내부 재시도로 흡수해 112가 보이지 않지만(왼쪽), 트랜잭션 안에서는 abort 후 112가 애플리케이션으로 던져진다(오른쪽)." width={1536} height={1024}>
  [그림] 같은 충돌이라도 트랜잭션 밖에서는 서버가 내부 재시도로 흡수해 112가 보이지 않지만(왼쪽), 트랜잭션 안에서는 abort 후 112가 애플리케이션으로 던져진다(오른쪽).
</Figure>

<strong>112가 애플리케이션까지 올라왔다는 것은, 그 쓰기가 트랜잭션으로 감싸여 있었다는 신호입니다. </strong>같은 충돌이 트랜잭션 밖에서 났다면 서버 내부에서 조용히 흡수됐을 테니까요.

따라서, 코드 내부에서충돌하는 쓰기가 어디인지, 그리고 그 쓰기가 왜 트랜잭션 안에 들어가 있는지 찾기로 하였습니다.

## 4. 충돌 위치 좁히기

배치 본문에서 DB 쓰기가 일어나는 곳부터 찾았습니다.

```java
@Transactional
public void removeExpiredChatLogFiles(LocalDate expiredAt) {
    List<ChatLogFileEntity> expiredFiles =
        chatLogFileRepository.findByExpiredAtLessThanEqual(expiredAt); // 조회(스냅샷만 잡음)
    if (expiredFiles.isEmpty()) return;

    List<Long> expiredIds = expiredFiles.stream().map(ChatLogFileEntity::getId).toList();
    chatLogFileRepository.deleteAllById(expiredIds);                   // ★ 유일한 DB 쓰기

    List<String> fileIds = expiredFiles.stream().map(ChatLogFileEntity::getFileId).toList();
    athenaClient.deleteChatFiles(fileIds);                            // fire-and-forget HTTP
}
```

이 메서드에서 DB 쓰기는 `deleteAllById` 하나뿐이었습니다. `findByExpiredAtLessThanEqual`은 조회라 스냅샷만 잡고 112를 던지지 않습니다. `athenaClient.deleteChatFiles`는 WebClient의 fire-and-forget HTTP 호출이라 애초에 트랜잭션 리소스가 아닙니다. 그러니 112가 표면화될 수 있는 지점은 `deleteAllById` 단 하나로 좁혀집니다.

그리고 메서드에는 `@Transactional`이 붙어 있었습니다. 3장의 기준대로라면, 바로 이 어노테이션이 `deleteAllById`의 충돌을 112로 끌어올린 스위치인 셈입니다.

## 4.1 충돌 상대는 둘 중 하나

실제 충돌 상대는 배치가 돌 때 같은 문서를 같은 시각에 쓰는 코드여야 합니다. 후보는 두 가지였습니다.

- <strong>시나리오 A — 다중 인스턴스 배치 자기 충돌</strong>: 이 배치 스케줄러에는 `@SchedulerLock`이 없었습니다. 애플리케이션이 2개 이상의 pod로 떠 있으면, 01:00 cron이 모든 인스턴스에서 동시에 발화합니다. 각 인스턴스가 동일한 만료 문서 집합을 조회해 같은 primary로 `deleteAllById`를 트랜잭션으로 보내면, 같은 문서를 동시에 삭제하면서 112가 납니다.
- <strong>시나리오 B — 단일 인스턴스 내 동시 API 충돌</strong>: 인스턴스가 1개여도 JVM은 멀티스레드입니다. 01:00 배치 스레드와, 같은 시각 들어온 파일 삭제 API 요청 스레드가 각자 트랜잭션을 열어 같은 문서를 삭제하면 충돌할 수 있습니다. 새벽 트래픽 특성상 확률은 낮지만 가능은 합니다.

한 가지 짚어둘 점이 있습니다. WriteConflict는 replica set 노드(primary/secondary) 사이의 문제가 아닙니다. 쓰기는 전부 primary 한 곳으로 모이고, 충돌은 그 단일 primary 위에 동시에 열린 여러 트랜잭션(세션) 사이에서 납니다. 동시 세션의 출처가 여러 인스턴스냐(A), 한 인스턴스의 여러 스레드냐(B)의 차이일 뿐입니다.

<Figure src="/posts/mongodb-writeconflict-112/05.png" alt="[그림 ] 여러 인스턴스의 스케줄러(A)와 한 인스턴스 안의 배치·API 스레드(B)에서 출발한 세션이 모두 단일 primary로 모여 충돌한다. secondary 노드는 충돌과 무관하다." width={1672} height={941}>

## 5. 정리하면, 근본 원인은 충돌이 아니었다

시나리오 A와 B 모두 원인은 “같은 문서에 대한 동시 쓰기”이고, 그 자체는 OCC 환경에서 정상적으로 일어날 수 있는 일이라는 점입니다.

여기서 2장과 3장의 동작 원리가 한 줄로 모입니다. 만약 이 `deleteAllById`가 트랜잭션 밖에 있었다면, mongod가 동일한 충돌을 내부에서 투명하게 재시도했을 것이고 클라이언트는 112를 보지 못했을 겁니다. 하지만 메서드에 `@Transactional`이 붙어 있었기 때문에, mongod는 내부 재시도를 포기하고 112를 던졌습니다. 그리고 이 코드에는 애플리케이션 수준의 재시도가 없었으니, 예외가 그대로 전파되어 배치가 중단됐습니다.

그래서 112의 근본 원인은 묶을 필요가 없는 단일 쓰기를 트랜잭션으로 감싸 충돌을 애플리케이션까지 끌어올린 것이었습니다.

## 6. 해결 — `@Transactional` 제거

제거를 결정한 근거는 세 가지였습니다.

<strong>묶어야 할 다중 쓰기가 없습니다.</strong> 이 메서드의 DB 쓰기는 `deleteAllById` 하나뿐입니다. `@Transactional`의 역할은 여러 쓰기를 전부-성공 / 전부-실패로 묶는 것인데, 묶을 대상 자체가 없었습니다.

<strong>원자성이 필요 없습니다.</strong> 만료 파일 N개 중 일부만 삭제되더라도 다음 배치가 나머지를 멱등하게 수거합니다. 1장에서 확인한 멱등성이 여기서 안전망이 됩니다.

<strong>비동기 호출은 영향을 받지 않습니다.</strong> fire-and-forget HTTP라 commit/rollback에 참여하지 않으므로, 제거 전후 동작이 동일합니다.

제거 후에는 동시 삭제가 발생해도 mongod가 문서별 충돌을 내부 재시도로 흡수하므로 112가 표면화되지 않습니다. 네트워크나 타임아웃 같은 비충돌 에러로 실패하더라도, 다음 날 배치가 멱등하게 재처리합니다.

## 7. 다른 선택지는 없었나

충돌을 다루는 방식은 크게 세 가지였습니다. 판단 기준은 “두 시나리오를 모두, 가능한 한 단순하게 덮을 수 있는가”였습니다.

`@SchedulerLock`은 "여러 인스턴스가 같은 job을 중복 실행"하는 것만 막으므로 시나리오 B를 해결하지 못합니다. 애플리케이션 retry는 두 시나리오를 다 덮지만, 이 단순한 멱등 배치에 백오프 전략까지 설계하는 건 과합니다. 출처와 무관하게 가장 단순하게 충돌을 흡수하는 방법이 트랜잭션 제거였습니다.

## 8. 배운 것

이번 추적에서 세 가지를 정리하게 됐습니다.

<strong>WriteConflict(112)는 “충돌이 났다”가 아니라 “서버가 충돌을 못 삼켰으니 애플리케이션이 재시도하라”는 신호입니다.</strong> <br />그 원인은 `@Transactial` 이였고 같은 충돌도 트랜잭션 밖에서는 서버가 조용히 재시도해 넘어갑니다.

`@Transactional`<strong>은 트랜잭션 리소스를 지배합니다.</strong> <br />같은 메서드 안에 있더라도 HTTP 호출 같은 비-DB 연산은 commit/rollback에 참여하지 않습니다. 트랜잭션이 무엇을 묶고 무엇을 안 묶는지를 "리소스" 단위로 봐야 합니다.

<strong>트랜잭션이 필요한지의 기준은 document 개수가 아니라 “원자적으로 함께 묶어야 할 별도 쓰기가 있는가”입니다.</strong> <br />한 번에 여러 문서를 지운다고 해서 트랜잭션이 필요한 게 아닙니다. 함께 성공하거나 함께 실패해야 할 서로 다른 쓰기가 있을 때 필요합니다.
