이전 두 편의 글에서 [하네스 엔지니어링](https://medium.com/%40evanbackeng/%EB%B0%94%EC%9D%B4%EB%B8%8C-%EC%BD%94%EB%94%A9%EC%9D%84-%EB%84%98%EC%96%B4-%ED%95%98%EB%84%A4%EC%8A%A4-%EC%97%94%EC%A7%80%EB%8B%88%EC%96%B4%EB%A7%81%EC%9C%BC%EB%A1%9C-ai-%EC%BD%94%EB%94%A9-%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%EC%97%90%EA%B2%8C-%EC%9E%90%EC%9C%A8%EC%9D%84-%EC%A3%BC%EB%90%98-%ED%86%B5%EC%A0%9C%EB%A5%BC-%EC%9E%83%EC%A7%80-%EC%95%8A%EB%8A%94-%EB%B2%95-d81ed296ae84)의 개념과 사용자의 의도대로 워킹하는 워크플로우를 만드는 법, 그리고 [AI 보조 엔지니어링과 바이브 코딩의 차이](https://medium.com/%40evanbackeng/%EB%B0%94%EC%9D%B4%EB%B8%8C-%EC%BD%94%EB%94%A9-%EB%84%88%EB%A8%B8-%EA%B0%9C%EB%B0%9C%EC%9E%90-%EC%83%9D%EC%A1%B4%EB%B2%95-%EC%9E%AC%ED%98%84%ED%95%A0-%EC%88%98-%EC%97%86%EB%8A%94-%EC%BD%94%EB%93%9C%EB%A5%BC-%EB%8F%8C%EC%95%84%EB%B3%B4%EB%A9%B0-e9987fd6a7a8)를 알아봤습니다.

이번에는 그 개념들을 사내에서 직접 쓸 수 있도록 구현해보고 싶었습니다. 핵심 자산은 spec문서로 잡았고, 그 위에서 동작하는 멀티에이전트 워크플로우를 설계했습니다.

대부분의 AI 코딩 콘텐츠는 그린필드를 가정합니다. 처음부터 spec을 깔고 가면 됩니다. 그런데 대부분의 개발자는 이미 워킹하는 브라운필드에서 개발을 하며, 도메인이 spec문서로 잘 정리되어 실시간으로 업데이트 되는 경우는 찾아보기 힘듭니다.

따라서 이번 글에서는 해당 워크플로우를 어떻게 설계하였는지 소개하는 글을 작성하고자 합니다.

## 1. 두 편의 글이 가리킨 LLM 워크플로우의 비용

세미나에서 Goos Kim님의 말이 계속 머리에 남았습니다.

> “에이전틱 코딩은 속도가 아니라 품질이 중요하다. 속도는 기본”

비용은 두 갈래에서 발생합니다.

하나는 컨텍스트 부족입니다. “재현할 수 없는 코드를 돌아보며"에서 적었듯이, 요구사항이 복잡한 기능을 두루뭉술하게 맡겼더니 구멍이 숭숭 뚫린 코드가 나왔습니다. AI가 못해서가 아니라 제가 준 컨텍스트가 부족했던 거였죠. 책 ‘바이브 코딩 너머 개발자 생존법’에서 말하는 ‘70% 문제’가 이 지점입니다. AI가 빠르게 만드는 70% 뒤의 30%(엣지 케이스, 보안, 유지보수성)는 결국 사람이 컨텍스트로 채워야 합니다.

다른 하나는 코드베이스를 매번 다시 스캔하는 비용입니다. 같은 도메인을 두 번째로 건드릴 때도 계획을 세우는 에이전트가 Controller → Service → Repository를 처음부터 다시 읽으면, 토큰은 누적되고 같은 추론이 반복됩니다. 워크플로우 한 번의 비용이 아니라, 돌릴 때마다 쌓이는 비용이죠.

두 비용은 같은 뿌리를 갖습니다. 시스템 정보가 코드에는 적혀 있는데, AI가 매번 그걸 다시 발견해야 한다는 점입니다. AI가 좀 더 효율적으로 일하게 하려면, 도메인 지식이 정적인 형태로 적혀 있어야 합니다.

## 2. 다시 고전으로: Bounded Context 단위의 spec문서

이 지점에서 도메인 주도 설계의 Bounded Context 개념으로 돌아갔습니다. 에릭 에반스가 정의한 Bounded Context는 한 도메인 모델이 적용되는 명시적 경계입니다. 각 컨텍스트는 자기만의 모델, 용어, 규칙을 자족적으로 가지고, 컨텍스트 사이의 관계는 Context Map으로 별도 명시됩니다.

LLM이 팀의 일원처럼 일하려면 이 경계가 어딘가에 명시되어 있어야 합니다. 사람 팀원은 컨텍스트의 경계를 회의나 코드 리뷰를 통해 머릿속에서 통합해 갈 수 있지만, AI는 그렇지 않습니다. 정적인 한 곳에 저장되어 있어야하고, 시스템이 변할 때마다 갱신 되어야 합니다.

따라서 도메인마다 한 장씩, 컨텍스트를 외부에서 이해하기 위한 정보를 담아 spec문서를 만들기로 하였습니다. 위치는 `.claude/docs/domains/<도메인>.md` 에 저장하기로 했습니다.

spec에 담을 항목은 한 Bounded Context를 묘사하는 세 묶음으로 정리하였습니다.

### 컨텍스트 내부

- 도메인 엔티티의 필드와 타입 (Aggregate / Entity)
- 비즈니스 규칙 (정책 분기, 핵심 상수)
- 핵심 설계 결정 (왜 이 구조를 잡았는가)

### 외부 노출 (Published Language)

- API 시그니처 (경로, HTTP 메서드, 요청·응답 DTO)
- 이벤트·비동기 계약 (페이로드, 알림 구조)
- 에러 계약(에러코드 체계, 예외 타입)

### 다른 컨텍스트와의 관계(Context Map)

- 다른 도메인에 대한 의존과 그 방식

이 묶음들의 공통점은 코드를 다시 읽지 않아도 답할 수 있어야 할 질문들이라는 점입니다. 도메인을 다음에 건드릴 때 plan-writer 에이전트가 spec문서만 읽고도 작업의 대부분을 설계 할 수 있다면, 다음 작업의 진입 비용이 매번 줄어듭니다.

## 3. context와 spec을 잇는 네 개의 에이전트

spec을 자산으로 두기로 했지만, 그것만으로는 부족했습니다. spec은 “현재 시스템이 어떻게 생겼는가"를 말해주지만, “이번에 뭘 하고싶은가"는 빠져 있기 때문이죠. 이 둘을 잇는 워크플로우가 필요했습니다.

흐름은 이렇게 잡았습니다.

<Figure src="/posts/bounded-context-spec-harness/02.png" alt="" width={1693} height={929} />

각 단계를 한 에이전트가 다 하면 컨텍스트가 무거워지고 책임이 뒤섞여 절차를 누락할 위험이 생깁니다. 그래서 4개의 에이전트에게 각각 다른 역할을 주었습니다.

- Plan-Writer: 합의된 요구사항과 spec을 같이 읽고, 구현자가 판단 없이 코드로 옮길 수 있는 계획을 작성합니다. spec이 baseline이라 코드 full-scan없이 계획을 세울 수 있습니다.
- Implementer: 계획을 그대로 코드로 옮깁니다. 설계 판단을 하지 않고, 모르는 부분은 TODO로 남깁니다.
- Test-writer: 변경된 클래스에 대한 단위 테스트를 작성합니다.
- Reviewr: 성공 기준과 반드시 유지할 항목, 그리고 테스트 통과 여부를 검증합니다. 실패 시 어떤 에이전트에게 돌려보낼지(retry\_target)를 명시합니다.

이 분업이 이전 글에서 적었던 “통제와 자율의 균형"의 구체적인 모습입니다. spec과 계획이 통제 역할을 하고, 그 안에서 구현과 테스트와 검증이 자율적으로 돌아갑니다.

마지막으로 모든 작업이 끝나면 메인세션이 spec문서를 갱신합니다. spec은 누적자산이라 한 번 오염되면 그 영향이 다음 작업으로 계속 번집니다. 그래서 모든 에이전트의 보고를 받아 전체 context를 알고 있는 메인 세션이 단독으로 spec문서를 갱신합니다.

## 4. spec문서가 없으면? — 브라운필드 진입 전략

AI 보조 엔지니어링과 바이브 코딩의 가장 큰 차이는 적용 환경에서 나뉩니다. 레거시가 이미 굴러가는 브라운필드인가, 처음부터 구성하는 그린필드인가. 보통의 개발자라면 수많은 도메인이 굴러가고 있는 환경에서 개발을 이어나갈 것이고, 이 경우 spec문서가 제대로 갖춰지지 않은 상황에서는 에이전틱 코딩을 쉽게 적용시킬 수 없습니다.

처음부터 모든 도메인의 spec문서를 만들 수 없으니 작업을 진행할 때 참고할 spec문서가 없으면 해당 작업을 완수 한 후 도메인을 분석하여 spec문서를 작성할 수 있도록 하였습니다. 혼자서 이 멀티에이전트를 사용한다면 모든 도메인을 한번씩 다 수정해야 시스템 전체의 spec문서를 작성할 수 있겠지만 저희 팀은 팀원들이 함께 사용하고 spec문서를 github으로 공유하니, 몇 주만에 도메인의 약 60\~70%의 spec문서가 작성되었습니다.

각 spec문서 내부에 ContextMap이 작성되므로, 도메인 간 관계까지 누적되어 에이전틱 코딩은 작업을 거듭할수록 더욱 정확해지고 견고해졌습니다.

## 5. 마치며 — 워크플로우의 품질을 만드는 두 가지

처음에는 워크플로우의 자산이 잘 짠 프롬프트라고 생각했습니다. 이전 두 글을 쓰고 이 시스템을 만들면서 다른 결론에 도달했습니다.

워크플로우의 품질을 만드는 건 두가지였습니다.

### 합의된 context

이번에 뭘 하고 싶은지를 메인 세션이 사용자와 함께 만드는 부분. 이게 부족하면 내 예상과 전혀 다른 결과물이 생성됩니다.

### 누적된 spec

시스템이 어떻게 생겼는지를 도메인마다 한 장씩 저장하는 부분. 이게 없으면 매 작업마다 같은 추론을 반복합니다.

이 둘이 갖춰져야 에이전트 분업이 제 역할을 합니다. 그리고 이 둘이 곧 “통제와 자율의 균형"의 양 축이기도 합니다. context와 spec으로 통제하고 그 안에서 에이전트들이 자율적으로 일하는 구조가 완성됩니다.
